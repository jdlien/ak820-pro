The same prompt as codex's (`review-prompt-ds-wake-unanchored.txt`), to
Claude Fable 5.1 at xhigh through the Claude CLI, with Read, Grep and Glob
only. It says it saw the existing lead list while searching the plans and
built its list from the code. Its companion is
`review-codex-ds-wake-unanchored-2026-10-31.md`.

Checked afterwards: its statement that every call in the wake window only
sets flags misses one. `pwm_tick_startI()` reaches `CT16B3_ResetTimer()`, an
unbounded spin on `CRST` under the lock (codex's finding; `sn32_ct.h:421-424`).

Its first cheap test, asked of JD on 10-31: was the board touched just before
the reset? JD: probably not. It lay on the bed beside JD, in view, unused, so

## The review, verbatim

I've read everything the question points at plus the LLDs the wake path touches. One disclosure first: while grepping `plans/BACKLOG.md` and `plans/GREMLIN-RESULTS.md` I did see the existing lead list there. The list below was built from the code, and it goes past that list.

## The frame every mechanism has to fit

- **The feed and the record.** The watchdog is fed in two places only: at the end of housekeeping, `ak820pro.c:668`, and once per counted second inside the sleep loop, `sleep.c:539`. The site is written at `sleep.c:434` and committed by the sacrificial write at `sleep.c:436`. The uptime is written at the *start* of housekeeping, `health.c:141`.
- **So "site 27, uptime frozen at entry" means:** the core left `deep_sleep()` neither by `return` nor by a reset of its own making. Everything between `sleep.c:434` and `sleep.c:627` is under site 27, including `recovery_begin()` and the window after `chSysUnlock()` at `sleep.c:612`. A hang in the *next* pass would carry site 1 or 3, because the leave write at return is followed by more SRAM writes at `sleep.c:968-969`, so it is committed.
- **Every loop the firmware owns in that window is bounded** and ends in `NVIC_SystemReset()`, which reads RSTST 0x01: `sleep.c:527-528`, `572-580`. The stray path breaks out at 1000 iterations of about 150 µs each, `sleep.c:559`. The RTC cannot stop while the watchdog keeps running, because both count on the ILRC. So the firmware as written cannot spend 11 s awake in this function. What is left is the core doing something not in the image, a handler that never lets the thread back, a bus that never answers, or the measured "does not count asleep" not holding on this unit.
- **The far Bluetooth host has no code path into the sleep.** UART2's receiver is off, `sleep.c:461`, the module is not a wake source, and nothing on the wake path touches the radio beyond setting flags, `ch582f_ajazz.c:1401-1406`. The only coupling I can find is the pack current a reconnecting module draws, used in mechanism 4 below.

## Mechanisms, ranked

**1. The USB block storms or wedges the moment interrupts come back, with the connector empty.** Path: during the sleep the hardware drops `PHY_EN` (manual p. 245). At the exit `usb_phy_onI()` sets `PHY_EN` only, `sleep.c:70-74, 608`; `DPPU_EN` is still set from `hal_usb_lld.c:472`, so D+ is pulled up and D- has no termination at all once the cable is out. Flags the block raised across the sleep sit pending with the IRQ disabled, and `NVIC->ISER[0] = iser` at `sleep.c:589` re-arms them; they run at `sleep.c:612`, inside the scope. The handler services exactly one bus flag per entry through an else-if chain, `hal_usb_lld.c:233-257`, clears nothing when `INSTS` reads 0 except setting `ESD_EN|PHY_EN`, `hal_usb_lld.c:224-228`, and never clears `mskERR_TIMEOUT` (bit 17) or `mskEP0_PRESETUP` (bit 24) outside the SETUP branch, `usbhw.h:14, 21`, `hal_usb_lld.c:271`. Any flag the hardware holds at level while the condition persists, or any enabled flag the chain never clears, is an interrupt at priority 1 that returns and re-enters forever: the main thread never runs, no feed, site 27, uptime frozen. Why it fits: it is the one place the code behaves differently with the cable *out* rather than cut by the relay. The bench's cut leaves D+/D- on the hub's pull-downs, `history/ds-phase-cableout-20261029/README.md:7-9`; out, D- floats and the exposed connector sits with the transceiver on and the ESD bit off. The bus state is undefined there. What it fails to explain: the loop must have exited first, so something woke the board at about 23:02:20; see the question in the tests. And white's 4 h 55 min cable-out sleep woke cleanly through this same code, as did black's three cable-out wakes since. Supporting doc: `docs/sn32f299.md` says USB is "Disable" in Deep-sleep (p. 78) and that `PHY_EN` auto-clears (p. 245), and is silent on what else in `USB_CFG` survives.

**2. The core runs something that is not the image after a wake, the errata item 37 class.** Path: every counted second the core wakes, runs `ds_deep_wfi()` from SRAM, `sleep.c:329-336`, and returns to flash at `sleep.c:536`. If that first fetch returns a stale or not-yet-ready block, the core executes garbage. Three endings all leave *this* record: a wild loop with no fault; a HardFault whose vector fetch at `0x0C` is itself bad, which is a lockup; or a fault inside the SRAM-less `_unhandled_exception` path never reached. The handler in `fault.c:50-75` only writes format 2 if it actually runs. Why it fits: no exit from the loop is needed, the hazard recurs about 400 times in an eight-minute sleep, and GREMLIN-RESULTS §21 notes the board was warm in bed and is a different unit, so a readiness margin could be that part's own. The 108 µs settle at `sleep.c:334` is explicitly unmeasured, `sleep.c:323-326`. What it fails to explain: the layout is fixed per build, so a deterministic stale-buffer artefact would fail every wake, as b2a0 did; a *rare* failure needs a timing tail such as flash wake-up time varying with temperature, and the 10-20 probe saw data reads correct from the first cycles on white at room temperature, `plans/DEEP-SLEEP-REGRESSION-2026-10-20.md:269-287`. White has since done over 100,000 second-wakes clean. Manual support: items 37 and 10 in `docs/sn32f299.md` sections 13 and 14; "which register powers the flash down in Deep-sleep, and the wake cost" is listed as unknown.

**3. The watchdog does count asleep on this unit, and the feed does not land.** The "does not count" result is from white only, `history/wdt-asleep-20261028-2330/README.md:11`; black has never run an unfed sleep. Even if black's WDT counted, the loop feeds once per second, so this also needs the feed to fail. There is a candidate: `SN_WDT->FEED` is written at `sleep.c:539` and the core is back in Deep-sleep within a few microseconds, far less than one ILRC period of about 30 µs. If the feed is synchronized into the ILRC domain, HCLK is gone before it latches. Why it fits: it is the one mechanism that needs no trigger and no software bug. Why it probably is not it: it would have reset every long sleep on black, and black slept ~30 min on earlier builds without one. It is listed because it is a three-minute test that has never been run on the right board.

**4. A supply transient with the LVD off, corrupting state the next wake runs on.** The LVD is off in Deep-sleep, `docs/sn32f299.md` p. 78 and section 3's "no brownout protection"; a dip below the core's limit leaves no `LVDRSTF`. The CH582F shares the pack and, with its host two floors away, is retrying at full power; `docs/wireless.md:240-246` shows the module alone drawing 15 mA for seconds after the MCU stops. Corrupted SRAM or registers then make the next wake behave like mechanism 2. Fits the far host and the cable out, since USB power masks the pack. Fails on likelihood: a healthy pack through the buck-boost should not sag that far. Cheap to kill with black's pack voltage at the time.

**5. A trigger, not a cause: something woke the board, and then 1 or 2 struck at the real wake.** Untouched wakes are available here: the knob wakes on either edge with no debounce, `sleep.c:487-488`; a column needs only a falling edge, and bedding pressing a key is a key; CHRG falls if the charger IC glitches as its input capacitor decays after the pull, and `battery.c:135-137` records that this charger pulses CHRG at ~2 Hz in some states. A normal wake then runs the recovery over later passes and would advance the uptime, so a trigger alone cannot produce this record. It only matters as the thing that hands control to mechanism 1.

**6. Theoretical only: the UART2 handler's unbounded loop.** `serve_interrupt` spins while `II` bit 0 reads 0, `hal_serial_lld.c:301` with `sn32_uart.h:256, 265`. A block whose registers read 0 or an interrupt ID the loop does not service would spin at priority 0 forever. I see no way this code reaches that state at a wake, but it is the only unbounded loop in any handler the unlock releases.

The SysTick handler the wake pends at `sleep.c:605` runs one virtual timer callback, `ch582f_ajazz.c:885-891`, which is trivial. The row ISR, the 20 kHz tick and the RTC handler are all bounded. I checked each callee in the window: `rtc_account_sleepI`, `rtc_wake_beginI`, `sn32f2xx_sleep_exitI`, `pwm_tick_startI`, `ch582_rx_resync`, `battery_sleep_wake`, `ch582_sleep_wake`, `display_sleep_wake`, `power_task`. They set flags and re-arm timers; none waits on hardware. GREMLIN-RESULTS §21's "every call after the unlock sets flags" holds.

**Cheapest tests, in order.**
- Ask JD whether a key was pressed, or the board moved in bed, at about 23:02:20. JD saw the banner at ~23:02, so a wake at 23:02:20 followed by an 11 s hang fits the timeline. A yes points at mechanism 1; a firm no points at 2.
- Run the unfed armed sleep on black: `scripts/deep_sleep.py --no-feed --no-press --cap 120`, when black is next on the bench. Kills or revives mechanism 3 on the unit that reset.
- Read black's battery log and the `5C` voltage around 23:02 on 10-28 from `~/Documents/ak820pro-battlogs/black/`. A pack above ~3.6 V kills mechanism 4.
- One dev build: the WDT in interrupt mode, `WDT_CFG.WDTIE = 1`, manual p. 152, with a handler at NVIC priority 0 on `fault.c`'s private stack that stores the stacked PC and exception number, `SN_USB->INSTS` and `CFG`, into a retained slot and then resets. That names the thread or the ISR the core was in at the timeout. No record at all means a PRIMASK spin or a lockup, which is mechanism 2's signature. This is the single test that separates 1 from 2 without waiting for the bus to be guessed right.
- For mechanism 1 without waiting for a repeat: a dev op that logs `INSTS`, `CFG`, `SGCTL`, `USB_DRIVER.state` and a USB-ISR entry count over the next 100 ms at each wake into the ring, run cable-out against hub-cut on black. Also settle whether the driver is `USB_ACTIVE` or `USB_SUSPENDED` after a real pull; the claim in `plans/BACKLOG.md:168-170` came from the data-cut case, `sleep.c:43-47`.
- For mechanism 2: the archived flash probe, `83371a49f2`, on black, warm, with reads at 10, 30, 60 and 100 µs after the wake; or lengthen the settle at `sleep.c:334` tenfold on black and repeat 10-28's shape for weeks.

## Can the record itself mislead

- **Site 27 is real but coarse.** It covers the loop, the clock restore, `recovery_begin()` and any handler that starves the thread from `sleep.c:612` to `627`. There is no nested `WDT_SCOPE` in that window, so the record cannot name anything finer. Warren's phases 28 to 31 exist to fix exactly that, and black runs them now.
- **Stale in the other direction is ruled out.** The posted-write loss of errata item 33 would need the leave write at return to be the last SRAM write before a spin; `rtc_pass_mark()` and `pass_t0` at `sleep.c:968-969` follow it. A hang after the return would read site 2 or 1.
- **The uptime proves less than it sounds.** It is written when housekeeping *starts*, `health.c:141`, so the next pass's matrix scan could have run. The site rules that out anyway.
- **RSTST is sound.** It is captured before the clear at `watchdog.c:65-72`, the previous boot cleared it, and `SWRSTF` is just its reset value, `docs/sn32f299.md` section 3. A `NVIC_SystemReset` reads 0x01, and the PLL and clock ceilings would therefore have produced an *invalid* record, since validity needs `RST_WDT`, `watchdog_record.c:71`. Consecutive 1 plus a boot at 23:02:32 means exactly one reset.
- **This boot's record.** The frozen uptime of 7,399,572 ms puts the entry at about 22:54:40 from a 20:51 boot, matching the pull at 22:54:38, so the record is not a leftover.
- **Could the timeout simply be short?** Warm, the ILRC runs about 35 kHz, so the timeout is about 11 s, still ten times the loop's feed interval. Only mechanism 3 lets the WDT fire with no hang.

## Things that look wrong even if they did not cause this

- **`usb_phy_onI()` restores half of what the hardware dropped.** The LLD always sets `ESD_EN|PHY_EN` together, `hal_usb_lld.c:226, 236, 248, 253`; the wake sets `PHY_EN` alone, `sleep.c:72`. After every deep sleep the ESD bit stays off until the next USB interrupt. Nothing checks `VREG33_EN`, `SIE_EN` or `DPPU_EN` survived, and the manual says USB is "Disable" in Deep-sleep, p. 78. Save `CFG` at entry and restore it whole, then read it back.
- **Pending USB flags are serviced inside the sleep's scope** with the state the driver had at the pull. Consider `INSTSC = ~0` at the exit, as `usb_lld_reset` does at `hal_usb_lld.c:539`, before `ISER` is restored.
- **The LLD can leave `INSTS` bits set forever**: `ERR_TIMEOUT` is never cleared; `EP0_PRESETUP` only inside the SETUP branch; `INSTS == 0` returns without clearing. Any of these asserting the line is a storm with no software bound.
- **The PLL and clock ceilings reset silently**, `sleep.c:528, 577, 580`: RSTST 0x01, record invalid, `ds_flags` lost. A `watchdog_record_stop()` before each would make a lock failure visible rather than looking like a flash.
- **The feed sits microseconds before HCLK stops**, `sleep.c:539`. Harmless while the WDT does not count asleep; an easy hardening is to feed before the GPIO reads so a full ILRC period passes before the WFI.
- **Entry discards every pending interrupt**, `sleep.c:479`, so the driver's view of the bus and the hardware's diverge for the whole sleep: the state can stay `USB_ACTIVE` with the PHY off, and `rtc_second_cb` keeps reading `SN_USB->FRMNO` on that basis, `rtc.c:631-639`.
- **One break disables line-status interrupts for good**, `hal_serial_lld.c:306`; nothing re-enables them. The module's TX line going low while it resets would silence framing and overrun reporting until `sdStart`.
- **The knob wakes on both edges with no settle**, `sleep.c:487-488`, and CHRG wakes on any falling edge. Both are credible "untouched" wakes; the dev ring would show them, and it is lost at a reset.
- **`DS_PLL_LOOPS` is tens of ms, not "~ms"**, `sleep.c:170`. Cosmetic.

What I am guessing at: the SN32 USB block's flag semantics on a floating bus, whether any `USB_CFG` bit other than `PHY_EN` is lost in Deep-sleep, and whether the WDT feed needs an ILRC edge to latch. None of those is in `docs/sn32f299.md`, and each has a test above that settles it without touching white.
