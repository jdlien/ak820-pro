This is a code review before a flash to a test board (gremlin's, never JD's). The change is firmware commit a03fc9d3 on qmk_firmware-ak820pro's branch gremlin/fill-poll, one commit on top of gremlin/config-menu's 4b899118 (the configuration menu's S0): `git -C qmk_firmware-ak820pro show a03fc9d3`.

The problem it fixes: the board's RGB matrix is driven by a row ISR (drivers/led/sn32f2xx.c) that re-arms its PWM counter at its END, so any delay to its start lengthens the dark gap for every LED row. SPI0 (the LCD panel) is driven by the ChibiOS SN32 SPI driver (lib/chibios-contrib/os/hal/ports/SN32/LLD/SN32F2xx/SPI/hal_spi_v2_lld.c), whose spiSend takes an RX-FIFO-threshold interrupt for every FIFO batch (8 bytes at 24 MHz, ~3 us apart), at priority 3, the same priority as the row ISR (docs/leds.md has the priority table). Measured on gremlin's board (plans/GREMLIN-RESULTS.md section 10, scripts/menu_s0_ledrate.py): while the menu fixture repaints with lcd_fill_rect, the row ISR rate falls from 3,726/s to 3,030/s (~19%) with its own duration unchanged, and JD sees every menu repaint flicker the keyboard's LEDs. Black clears are DMA'd from flash (lcd_clear_rect_ok) and cost the LEDs nothing; colour fills can't be DMA'd, because the SN32 DMA is SPI-to-SPI only.

The change: spi0_poll_send() in keyboards/a_jazz/ak820pro/graphics/lcd_bus.c feeds SPI0's FIFO from the main thread with SN_SPI0->IE cleared (RXFIFOTHIE off), at most 8 bytes outstanding, drains RX, waits out BUSY, clears RXFIFOTHIC with a literal write, and sets IE back to 0b0100. lcd_fill_rect, tx_pixels (lcd_blit_ram and other RAM pixel pushes) and lcd_stream_bytes use it; commands, the window (lcd_window) and single bytes stay on spiSend (tx8). A bounded spin gives up, resets the FIFOs, counts, and on dev builds sets a new sticky bit PO_FAIL_SPI0_POLL (menu/panel_owner.h).

Please review, adversarially, for correctness and safety on this hardware:
1. The interrupt hand-off with the ChibiOS driver. Is the driver idle at every call site (every caller calls bus_quiesce() or otherwise follows a completed spiSend)? Can a stale RIS flag, an NVIC pending bit, or residue in either FIFO make SN32_SPI0_HANDLER run the driver's completion code (__spi_isr_complete_code) while no transfer is in flight, or corrupt the next spiSend's txidx/rxidx accounting? Is clearing IE, rather than disabling the NVIC vector, right, given SN32_SPI0_HANDLER also services the flash->LCD DMA completion (sn32_flash_dma_isr)? Is there any path where a DMA is armed, in flight, or started (by an ISR, a callback, the animation, the glyph pump) while a polled send runs?
2. The FIFO loop itself: the TX_FULL/RX_EMPTY/BUSY semantics as the driver and lcd_bus.c's own spi1_raw_byte use them; whether the RX FIFO can overflow; the final drain; DFDLY; whether 8-bit frames read and written through DATA match the driver's.
3. The bound: SPI0_POLL_SPIN_PER_BYTE 64 per byte plus 1000, counted per outer-loop iteration while the row ISR (~200 us a run, ~74% of the CPU) preempts the loop. Can a healthy 512-byte chunk ever trip it? What does the board look like after a give-up (CS, the panel's window, the next spiSend)? Is a give-up reported where anyone will see it?
4. Interactions: the watchdog scopes, the main loop's stall counters (count_ge_10ms, count_ge_25ms: a fill now runs longer in wall time because the row ISR preempts it, so can any single pass cross 25 ms where it didn't?), the backlight PWM ISR at priority 2, USB, and the CH582F UART at its priority.
5. Anything else that would make flashing this to gremlin's board unsafe, or the measurement it's for misleading.

For each finding: severity (blocker / should-fix / note), the file and line, the failure scenario, and the fix you'd make. If it is safe to flash to the test board as it is, say so plainly.
