# The SN32F299: a working reference for this board's MCU

The AK820 Pro runs on a Sonix **SN32F299F** (Cortex-M0, LQFP80; JD's unit
carries an `HFD80CP100`, a clone, see [battery.md](battery.md), "The pin
audit"). This file distils the vendor's *SN32F290 Series User's Manual*,
version 1.8 (2025-12-19, 273 pages), into what firmware work on this board
needs, and puts each fact next to the code that depends on it. The manual is
in the reference repo: `../ajazz-ak820-pro/docs/SN32F299_V1.8_EN.pdf`.

**How to use this file.** Look the fact up here first; open the PDF only to
check a page. Every manual fact carries its page, `(p. 75)`. The PDF's page
index and the printed page number agree on every page, so `(p. 75)` is both.
Four markers flag what is not a plain manual fact:

- **Inferred:** reasoned from the manual or the code, not stated anywhere.
  Verify before building on it.
- **Silent:** the manual does not say. Measure it.
- **Conflict:** the manual says two different things, or the manual and this
  board disagree. Both are given.
- **Board:** what our firmware does, or what was measured on JD's unit.

Code paths are abbreviated. `kb/` is
`qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/`, `qmk/` is
`qmk_firmware-ak820pro/`, `contrib/` is
`qmk_firmware-ak820pro/lib/chibios-contrib/os/`. Line numbers are from the
working tree on 2026-10-18 (firmware `460ca22840` plus uncommitted edits,
chibios-contrib `a4f8412134`); they drift, so search for the symbol if a
number is off.

QMK pin names map **`A`→P0, `B`→P1, `C`→P2, `D`→P3** (`A11` is P0.11);
verified in [battery.md](battery.md) and by `GPIOA = SN_GPIO0_BASE`
(`contrib/hal/ports/SN32/LLD/SN32F2xx/GPIO/hal_pal_lld.h:42-45`).

## 1. At a glance

| | |
|---|---|
| Core | ARM Cortex-M0, little-endian, 32 IRQs, **4 priority levels (2 bits)** (p. 43, 45-46) |
| Max clock | HCLK/CPU 48 MHz (p. 16-17). Timer PCLK "up to 96 MHz" from the PLL VCO (p. 16, 114) |
| Flash | 256 KB user ROM, 256 pages of **1 KB**; 4 KB boot ROM (p. 16, 251-252) |
| SRAM | 32 KB at `0x2000_0000` (p. 16, 39) |
| Package | LQFP80, 10 mm body, 12 mm over leads, **0.4 mm pitch** (p. 267); 74 GPIO (p. 17) |
| Supply | VDD 2.5-5.5 V; 3.1-5.25 V when USB is used (p. 263). Absolute maximum is also 5.5 V (p. 263) |
| Oscillators | IHRC 12 MHz, ILRC ~32 kHz, optional 10-25 MHz and 32.768 kHz crystals, PLL (p. 57-60). **Board: no crystal is fitted**; both crystal pin pairs drive RGB rows ([battery.md](battery.md)) |
| Modes | Normal, Sleep, Deep-sleep (p. 74) |
| Peripherals | 6 × 16-bit CT16 timers (28 PWM outputs + 8 inverted), WDT, RTC, 2 SPI (SPI0 has a SPI-to-SPI DMA), 4 UART, 2 I2C, 2 I2S, 12-bit ADC (16 pins + 3 internal), 3 comparators, 2 op-amps, segment-LCD driver, EBI/8080, CRC, USB FS device (p. 16-18) |
| Typical current | 11 mA at 48 MHz, Deep-sleep 2 µA, both at VDD 3.3 V (p. 263) |

**Board:** VDD is **not** 3.3 V here. It reads 3.90 V on battery (a
buck-boost's output) and 4.47-4.79 V on USB ([battery.md](battery.md), "VDD
by power state"). The 3.3 V parts (LCD, SPI flash) hang off the VDDIO1 rail
([section 6](#voltage-domains-vdd-and-vddio1)).

**How this board lays the flash out:**

- The application starts at `0x0` (`contrib/common/startup/ARMCMx/compilers/GCC/ld/SN32F290.ld`).
- The last word, `0x3FFFC`, is a `.flag` section (`SN32F290.ld:95-101`).
  **Silent:** the manual never mentions it. **Inferred:** a marker the Sonix
  bootloader checks.
- The wear-levelled EEPROM is 2 KB (`WEAR_LEVELING_BACKING_SIZE`,
  `qmk/platforms/chibios/drivers/wear_leveling/wear_leveling_efl_config.h:68`)
  placed just below the last page, which is kept out by
  `WEAR_LEVELING_EFL_OMIT_LAST_SECTOR_COUNT 1`
  (`qmk/platforms/chibios/boards/SN_SN32F290/configs/config.h:22-23`).
  **Inferred:** pages 253-254, `0x3_F400`-`0x3_FBFF`.
- The CRC unit's ROM mode checks "the User ROM, except the last page"
  (p. 236), so the last page is special to the vendor too.
- The top 16 B of SRAM (`0x2000_7FF0`) is `ram7`: reset-retained and never
  initialized. The watchdog's boot accounting lives there, and the
  bootloader magic sits just below it (`SN32F290.ld:30-44`, `kb/watchdog.c`).

**Vector table location.** `SYS0_IVTM` (offset `0x24`, key `0xA5A5` in bits
31:16) maps the vector table to the boot ROM or to user ROM 1-4, the four
64 KB quarters of flash (p. 66). Its reset value follows `BLEN` in the code
option. **Conflict:** the prose says it can map to SRAM, but the field
defines no SRAM encoding. So vectors cannot be moved to RAM, which is why
an interrupt taken during a flash program window fetches from the array
being programmed ([section 10](#10-internal-flash-controller)).

## 3. Clocks, resets and system control

### Clock sources

| Source | Facts |
|---|---|
| **IHRC** 12 MHz | On at reset; the system clock after any reset (p. 61). Enable `SYS0_ANBCTRL.IHRCEN` (bit 0, reset 1). Accuracy: **Conflict:** ±0.2% "under commercial condition" (p. 57) against 11.76-12.24 MHz at 25 °C and 11.70-12.30 MHz over -40..85 °C, i.e. ±2-2.5% (p. 265). The graph on p. 265 shows 11.99-12.09 MHz across 2.5-6 V and every temperature, rising about 0.6% from 2.5 V to 6 V. Trimmable through `SYS0_IHRCADJ` (offset `0x34`, key `0xA5A5`; `ADJ[7:0]`, `DIR`, `ADJEN`; "400 counts", each step 0.2-0.3%, p. 67-68). **Board:** the CT16B5 system timebase, which is IHRC × 4 / 256, reads within 0.01-0.04% of the host's wall clock ([leds.md](leds.md), `timebase_vs_wall`). That fits the ±0.2% figure and explains why USB works with no crystal. |
| **ILRC** ~32 kHz | An untrimmed RC. **"Can ONLY be switched on and off by HW"** (p. 57): there is no enable bit. Clocks the WDT (p. 150), and optionally the RTC (p. 156), the LCD driver (p. 202) and the system clock. **Conflict:** called 16 kHz (p. 57, 202), 32 kHz (p. 16, 57) and 32.768 kHz (p. 19). The graph on p. 265 is what matters: flat against VDD, **steep with temperature**, about 44.5 kHz at -40 °C, 39.4 kHz at 0 °C, 36.5 kHz at 25 °C, 35.1 kHz at 40 °C, 33.4 kHz at 60 °C and 31.3 kHz at 85 °C. **Board:** ~33.6 kHz on JD's unit (`kb/config.h:340`, `RTC_PERIOD_INITIAL 33600`), wandering with warmth; that is the whole story of [clock.md](clock.md), "The 5-minute sawtooth". |
| **EHS** crystal 10-25 MHz | `ANBCTRL.EHSEN` (bit 4), `EHSFREQ` (bit 5: 0 for ≤ 12 MHz, 1 above). Warm-up 2048 clocks. Pins P3.12/P3.13 (p. 59-60). **Board:** not fitted; P3.12/P3.13 are RGB rows. |
| **ELS** crystal 32.768 kHz | `ANBCTRL.ELSEN` (bit 2). Pins P3.10/P3.11 (p. 60). **Board:** not fitted; P3.10/P3.11 are RGB rows. So the RTC must run on the ILRC, and CT16B5 cannot use ELS. |
| **PLL** | Input 10-25 MHz from the IHRC or EHS. VCO 96 MHz (p. 58; the constraint on p. 63 reads "96 MHz ≤ FVCO"). `FVCO = FIN × M`, `FOUT = FVCO / P`, M ∈ {4, 6, 8, 10, 12}, P ∈ {2, 4}. **Settling 100 µs** (p. 58). "48 MHz if USB is enabled" (p. 19). |

**How this board makes 48 MHz** (`contrib/common/ext/SONiX/SN32F2xx/system_SN32F290.c:97-126, 262-322`):
IHRC 12 MHz → PLL with `MSEL = 010` (M = 8) and `PSEL = 0` (P = 2) → VCO
96 MHz → 48 MHz → `SYSCLKSEL = 100` (PLL) → `AHBPRE = /1` → **HCLK 48 MHz**.
That is the manual's own recommended setting (p. 63). `SystemInit()` writes
`FLASH_LPCTRL = 0x5AFA0039` before starting the PLL, then
`FlashClockUpdate()` sets `0x5AFA0029`, the value for 24 < HCLK ≤ 48 MHz
(p. 255, `system_SN32F290.c:226-237`). **Board:** do not re-set LPCTRL to
`0x39`; it slowed instruction fetch about 5% (`kb/graphics/lcd_bus.c:105-108`).

`SN32_HCLK` is the runtime variable `SystemCoreClock`
(`contrib/hal/ports/SN32/SN32F290/hal_lld.h:54`). The UART baud divisor, the
PWM prescalers, the ST prescaler and the SPI dividers are all computed from
it at start-up, so **changing the system clock at run time invalidates every
one of them** (Inferred, from the drivers).

### System clock switching (SYS0, base `0x4006_0000`)

| Offset | Register | What matters (p. 62-68) |
|---|---|---|
| `0x00` | `ANBCTRL` | `IHRCEN` b0 (reset 1), `ELSEN` b2, `EHSEN` b4, `EHSFREQ` b5. An enable cannot be cleared while that source is, or is about to be, the system clock. |
| `0x04` | `PLLCTRL` | `MSEL[2:0]` (000=4, 001=6, 010=8, 011=10, 100=12), `PSEL` b5 (0: P=2, 1: P=4), `PLLCLKSEL` b12 (0 IHRC, 1 EHS), `PLLEN` b15. `PLLEN` cannot be cleared while the PLL is in use. |
| `0x08` | `CSST` | Ready flags: `IHRCRDY` b0 (reset 1), `ELSRDY` b2, `EHSRDY` b4, `PLLRDY` b6. |
| `0x0C` | `CLKCFG` | `SYSCLKSEL[2:0]` (000 IHRC, 001 ILRC, 010 EHS, 011 ELS, 100 PLL); `SYSCLKST[6:4]` reports the clock actually in use. A switch happens only once the target is ready; select an unready one and the switch waits (p. 61). |
| `0x10` | `AHBCP` | `AHBPRE[2:0]`: HCLK = SYSCLK / 1, 2, 4 ... 128. `DIV1P5` b3: SYSCLK / 1.5. |
| `0x14` | `RSTST` | Reset flags, [below](#reset-sources-and-rstst). |
| `0x18` | `LVDCTRL` | [Below](#low-voltage-detector-lvd). |
| `0x1C` | `EXRSTCTRL` | `RESETDIS` b0: 1 makes P3.7 a GPIO. Writable only if the code option's `EXTRSTHWDIS` is 1 (p. 65-66). |
| `0x20` | `SWDCTRL` | `SWDDIS` b0: 1 turns P3.5/P3.6 into GPIO, which ends SWD debugging until the BOOT pin is used (p. 66, 258). |
| `0x24` | `IVTM` | Vector mapping, see [section 2](#2-memory-map). |
| `0x28`/`0x2C` | `NDTCTRL`/`NDTSTS` | 5 V-domain noise detector, IRQ0 (p. 67). Unused here. |
| `0x30` | `ANTIEFT` | Hardware anti-EFT strength (p. 67). Unused here. |
| `0x34` | `IHRCADJ` | IHRC trim, above. |

**Clock-out.** `SYS1_AHBCLKEN.CLKOUTSEL[30:28]` selects one of ILRC, ELS,
HCLK, IHRC, EHS or PLL, with `SYS1_APBCP1.CLKOUTPRE` as its divider. "HW will
replace GPIO with CLKOUT directly if CLKOUTSEL is not 0" (p. 69), on P3.0.
**Board:** P3.0 is SPI0's SCK to the LCD. Never set `CLKOUTSEL` on this board.

**Flash wait states** (`FLASH_LPCTRL`, p. 255): `LPMODE` must be `000000`
for HCLK ≤ 24 MHz, `101001` for 24-48 MHz and `111001` above 48 MHz; any
other value "may cause unexpected error to force MCU enter Hard fault". Key
`0x5AFA` in bits 31:16. **Silent:** the order relative to a clock switch.
**Inferred:** raise LPMODE before speeding up and lower it after slowing
down; the CMSIS `SlowModeSwitch()` switches to the IHRC first, then writes
`0x5AFA0000` (`system_SN32F290.c:246-251`).

### Clock gating, prescalers and peripheral resets (SYS1, base `0x4005_E000`)

**`AHBCLKEN` (offset `0x00`)** gates each block's clock (p. 69-70). A gated
block's registers may read as 0 (p. 69). Bits: OPA 3, USB 4, CT16B0-B5 5-10,
ADC 11, SPI0 12, SPI1 13, CMP 14, EBI 15, UART0-3 16-19, I2C1 20, I2C0 21,
I2S0 22, RTC 23, **WDT 24 (reset 1)**, I2S1 25, LCD 26, CRC 27, `CLKOUTSEL`
30:28. **GPIO, flash, SRAM and PMU have no gate**; ChibiOS's
`sys1EnableGPIOn()` are empty macros
(`contrib/hal/ports/SN32/SN32F290/sn32_sys1.h:125-128`).
**Conflict:** `WDTCLKEN = 0` is "Reserved" (p. 69), yet p. 150 says the WDT
register clock "can be disabled ... for power savings".

**Board:** `lcd_bus.c` enables the **EBI (15) and LCD (26) clocks** for the
SPI-to-SPI DMA, "shared DMA datapath" (`kb/graphics/lcd_bus.c:104`). The
manual never states that requirement. The SPI DMA is documented inside the
EBI chapter (p. 166, 224), which is probably why those clocks matter.

**Prescalers.** Only four blocks have one: the ADC (`APBCP0.ADCPRE[18:16]`,
HCLK / 1 ... / 16, p. 70-71), and in `APBCP1` (offset `0x08`) the WDT
(`WDTPRE[22:20]`, its source / 1, 2, 4, 8, 16, 32), the I2C0/I2C1
(`I2CnPRE`, write-only fields), the I2S and the clock-out (p. 71-72). SPI,
UART and CT16 run straight off HCLK (**Inferred** from the clock diagram,
p. 19, and the absence of fields). "Must reset the corresponding peripheral
with `SYS1_PRST` after changing the prescale value" (p. 70-71). **Board:**
both writers obey it: `battery.c` resets the ADC
(`kb/battery.c:98-104`), `watchdog.c` the WDT (`kb/watchdog.c:97-99`).

**`PRST` (offset `0x10`)** holds one reset bit per block (p. 72-73): GPIO
P0-P3 0-3, EBI 4, CT16B0-B5 5-10, ADC 11, SPI0 12, SPI1 13, CMP 14, LCD 15,
UART0-3 16-19, I2C1 20, I2C0 21, I2S0 22, RTC 23, WDT 24, I2S1 25, CRC 26,
OPA 28. (Bit 8 is captioned "CT32B0", a typo for CT16B3.)

### Reset sources and RSTST

Five sources: the RESET pin (P3.7, low-active Schmitt input), POR, LVD, WDT
and software (`AIRCR.SYSRESETREQ` with `VECTKEY 0x05FA`) (p. 46, 49-56). After
POR, WDT and external resets, execution starts in the **boot ROM if the code
option's `BLEN` = 1** (the default), otherwise at `0x0` (p. 49-53).

`SYS0_RSTST` (offset `0x14`, p. 64-65): `SWRSTF` b0, `WDTRSTF` b1, `LVDRSTF`
b2, `EXTRSTF` b3, `PORRSTF` b4. Sticky; **write 0 to clear**. Reset values
are `PORRSTF = 1` **and `SWRSTF = 1`**.

**Board** (`kb/watchdog.c:65-72`, [hardware.md](hardware.md)): reads `0x11`
(POR + SW) after a cold power-on and `0x05` (LVD + SW) after a slider
brownout. Both fit `SWRSTF`'s reset value of 1: **a set `SWRSTF` does not
by itself mean software asked for a reset**. Only `WDTRSTF`, `LVDRSTF`,
`EXTRSTF` and `PORRSTF` are diagnostic. `watchdog.c` captures the register,
then writes 0 so each boot names its own cause.

### Low-voltage detector (LVD)

`SYS0_LVDCTRL` (offset `0x18`, p. 65):

- `LVDEN` b15 and `LVDRSTEN` b14 have **inverted polarity**: 0 enables.
- `LVDINTLVL[6:4]` and `LVDRSTLVL[2:0]`: 100 = 2.70 V, 101 = 3.60 V,
  011 (the reset value) "reserved for booting".

The electrical table gives three levels, 2.60-2.80, 2.90-3.10 and
3.50-3.70 V (p. 265). **Conflict:** the register lists only two of them
(p. 16 and p. 265 have 3.0 V; p. 65 has no encoding for it). The LVD
interrupt is IRQ26.

**Board:** nothing writes `LVDCTRL`, so the LVD runs at its reset settings,
reset enabled, at the "reserved for booting" level. It is what reboots the
board on most slider flips ([hardware.md](hardware.md)). The LVD is off in
Deep-sleep (p. 78), so a Deep-sleep board has **no brownout protection**
(Inferred).

### Code option, BOOT pin, bootloader

- **Code option word** at `0x1FFF_2000` (p. 47):
  - `CS[31:16]` code security: `0xFFFF` is CS0, `0x5A5A` CS1, anything else
    CS2 (p. 47; what each level allows, p. 253).
  - `BOOTPINEN` b2 (default 1).
  - `EXTRSTHWDIS` b1 (default 1: firmware may control the RESET pin).
  - `BLEN` b0 (default 1: boot through the ROM).
- **BOOT pin = P1.3** (pin 74). The ROM samples it at boot; low keeps the
  chip in the bootloader. The manual warns against using it as an LED drive
  (p. 20, 28, 258). **Board:** P1.3 has no firmware use; the 2-pin pad under
  the space bar shorts it.
- **The bootloader.** **Conflict:** the manual says the boot ROM
  reprograms flash over **UART0** (p. 252). This board's bootloader
  enumerates on **USB as `0C45:7140`** ([hardware.md](hardware.md)). QMK
  enters it with a RAM magic (`0xDEADBEEF` at the top of `ram0`) and a jump
  to `0x1FFF_0301` (`qmk/platforms/chibios/bootloaders/sn32_dfu.c:25-40`,
  `qmk/platforms/chibios/mcu_selection.mk:1087`). **Silent:** the entry
  point, the USB protocol and the `0x3FFFC` flag. **Board:** leaving it
  without a flash needs a cold power-off ([hardware.md](hardware.md)).

## 4. Power management: Sleep and Deep-sleep

This is the section the sleep work needs. Read it whole before building
either mode.

### The modes (p. 74-79)

| | Normal | **Sleep** | **Deep-sleep** |
|---|---|---|---|
| Enter | — | `PMU_CTRL = 4`, then `WFI` | `PMU_CTRL = 2`, then `WFI` |
| CPU | runs | clock stopped | clock stopped |
| IHRC / EHS / PLL | per their enables | **per their enables** (stay on unless firmware turns them off) | **off** |
| ILRC | on | on | on only if it clocks the RTC or LCD |
| ELS | per enable | per enable | on only if it clocks the RTC, LCD or CT16B5 |
| Peripherals | per `AHBCLKEN` | **keep running** per `AHBCLKEN`, and their interrupts wake the CPU | HCLK removed: every peripheral stops except the RTC and LCD (and CT16B5 if on ELS) |
| Flash | on | "Disable" (table) | "Disable" |
| SRAM, CPU registers, peripheral registers | | kept | kept |
| Pins | | levels held | levels held |
| USB / ADC / LVD / CMP / OPA | per enables | per enables (**Conflict:** USB, below) | all off |
| Wake sources | — | **any interrupt**, the RESET pin | **GPIO edge interrupt, RTC, LCD**, (CT16B5), the RESET pin |
| Wake time | — | **none** if the high clock was left running; otherwise 2048 EHS clocks + 32 IHRC clocks | 10 µs + 32 IHRC clocks ≈ **12.7 µs** (IHRC); 10 µs + 2048 EHS clocks + start-up (crystal) |
| Supply current (p. 263, 265) | 11 mA at 48 MHz | **only figure: 300 µA**, at SYSCLK = 32 kHz (ILRC), IHRC and PLL off, VDD 5 V | **2 µA typ**, VDD 3.3 V; graph: ~0.5 µA at 0 °C, ~1.2 µA at 25 °C, ~2 µA at 40 °C, ~5 µA at 60 °C, ~16 µA at 85 °C |

`PMU` is at `0x4003_2000`; **`PMU_CTRL` is at offset `0x40`
(`0x4003_2040`)**. `MODE[2:0]`: 000 disabled, 010 Deep-sleep on WFI, 100
Sleep on WFI, the rest reserved (p. 79). The manual describes no use of the
Cortex `SCB->SCR.SLEEPDEEP` bit; the PMU register alone picks the mode.
**Silent:** what `WFI` does with `MODE = 000`. **Inferred:** a plain core
clock-gate, but that is not stated.

**Manual inconsistencies in this chapter:**

- "Four operating modes" are announced and three listed; "three special
  modes" are announced and two listed (p. 74).
- **Conflict, Deep-sleep wake sources:** the text lists GPIO, RTC, LCD and
  RESET (p. 76). The state machine (p. 77) and the comparison table
  (p. 78) add **CT16B5**. CT16B5 can only keep counting in Deep-sleep on the
  ELS crystal (p. 78, 125); **this board has none**, so CT16B5 is no wake
  source here.
- **Conflict, ILRC:** a note added in v1.8 says the user "SHALL decide to
  power down" the ILRC or ELS if the RTC or LCD is enabled (p. 75), but the
  ILRC has no enable bit and "can ONLY be switched on and off by HW"
  (p. 57). **Inferred:** the ILRC stays on in Deep-sleep exactly when the
  RTC (or LCD) is enabled with ILRC as its source, and the way to turn it
  off is to disable the RTC.
- **Conflict, USB in Sleep:** the table puts USB "By USBEN" in Sleep
  (p. 78), but `USB_CFG.PHY_EN` "will be automatically disabled if entering
  sleep mode, deep-sleep mode" (p. 245). If p. 245 is right, **PMU Sleep
  drops the USB transceiver**, which matters whenever USB is attached
  (cable mode, or charging on the bench). Weak evidence against it: until
  2026-08-28 the idle thread did PMU Sleep + WFI (board `chconf.h` plus
  `CORTEX_ENABLE_WFI_IDLE TRUE`) and the board was used on USB. But QMK's
  main loop never blocks except inside `wait_ms()`, so the idle thread
  seldom ran (Inferred), and that proves little. **Measure it.**
- **Flash:** the table says it is disabled in Sleep too (p. 78), while the
  text says it "can be powered down in Deep-sleep" at the cost of a longer
  wake (p. 75). **Silent:** which register chooses that, and the cost.

### Sleep in detail (p. 74-76)

- The core clock stops; every peripheral enabled in `AHBCLKEN` keeps
  running and any enabled interrupt wakes the core.
- Analog blocks keep whatever their enable bits say. **Sleep does not, by
  itself, save the PLL's or IHRC's current.** The 300 µA figure was taken
  with the system clock moved to the ILRC and the IHRC and PLL off (p. 263,
  notes 6 and 8). It is a USB-suspend number, not a "light sleep at 48 MHz"
  number.
- **Silent:** the current in Sleep at 48 MHz. Expect the core's dynamic
  share of the 11 mA to go and the PLL, IHRC, flash (if it really powers
  down) and running peripherals to stay. Measure it.
- Port-2 pins used as ADC inputs must be set input, "inactive", Schmitt
  trigger off and data low, or they leak (p. 75, 97-98). The ADC should be
  disabled (`ADENB = 0`) before either low-power mode (p. 96).
- **Silent:** whether SysTick keeps counting in Sleep. The SysTick section
  warns that "some implementations stop this clock signal for low power
  mode" without saying whether this one does (p. 41). This matters because
  ChibiOS's tick-less mode uses **SysTick as the alarm**
  ([section 7](#ct16b5-chibioss-system-timer)). If SysTick stops in Sleep, every
  `chThdSleep()` and virtual-timer deadline runs late by the time spent
  asleep. The health page's `timebase_vs_wall` and the `[pwmtick]` canary
  ([leds.md](leds.md)) will show it.

### Deep-sleep in detail (p. 75-78)

- Every oscillator except a low-speed one in use stops, and with it every
  peripheral clock. State, SRAM and pin levels are kept.
- **Wake by pin is edge-only.** "All GPIO pins are served as wakeup pins",
  but only edge-sensitive interrupts wake. The pin's GPIO interrupt must be
  configured (`IS = 0`, `IBS` or `IEV`, `IE = 1`) **and its port's IRQ
  enabled in the NVIC**. "Strongly recommended" to use both edges (p. 75).
  P0 → IRQ31, P1 → IRQ30, P2 → IRQ29, P3 → IRQ28 (p. 44).
- Debugging is not supported in Deep-sleep (p. 74).
- Unbonded or unused pins should be inputs with pull-up (p. 21, 74, 79).
  The 2 µA figure assumes every pin is an output driven low with pull-ups off
  (p. 263, note 1).
- **Silent: what clock the chip runs on after waking.** The manual gives
  the wake time as 10 µs plus the IHRC (or EHS) warm-up (p. 76) and says
  nothing about the PLL. **Inferred, and the safe assumption:** the core
  resumes on the IHRC or with the PLL unlocked. After waking, check
  `SYS0_CLKCFG.SYSCLKST` and `CSST.PLLRDY`, re-enable the PLL, wait for
  `PLLRDY` (≤ 100 µs, p. 58), switch back, and restore `FLASH_LPCTRL`.
  Re-running `SystemInit()` then `FlashClockUpdate()` (what
  `hal_lld_init()` does, `contrib/hal/ports/SN32/SN32F290/hal_lld.c:59-72`)
  covers this. Until that is verified, nothing clocked from HCLK can be
  trusted to have kept its rate.
- **What stops and must be restarted or re-checked after waking**
  (Inferred from the table and the drivers): the CT16B5 ChibiOS time
  counter and SysTick (system time freezes across the sleep; account for
  the gap before trusting timers); the three RGB PWM timers and the 20 kHz
  GPT; SPI0 and SPI1 (any DMA in flight is lost, so never sleep with a blit
  armed); UART2 (bytes arriving while asleep are lost; see the
  [CH582F note](#deep-sleep-on-this-board-wake-on-keypress)); the ADC (and
  its 100 µs enable time, p. 96); the USB block (it is "Disable"; a host
  would see a dead device; Deep-sleep only makes sense on battery); the LVD.

### Prerequisites the manual imposes before either mode

1. ADC off: `ADC_ADM.ADENB = 0` (p. 96, 99). **Board:** `battery.c` leaves
   `ADENB` set permanently (`ADM_BASE`, `kb/battery.c:58-60`); the ADC draws
   about 100 µA (p. 264).
2. Port-2 analog pins inactive (p. 75, 97). **Board:** the ADC reads the
   internal AIN16, which has no pin, so no port-2 pin is in analog mode.
3. Unused pins as inputs with pull-up (p. 74, 79).
4. For Deep-sleep: wake pins on edge interrupts with NVIC lines enabled
   (p. 75); the RTC on the ILRC if timed wakes are wanted (p. 75-78).
5. The watchdog: see the next item.

### The watchdog and low power

The WDT counts on the ILRC (p. 150), and "Watchdog reset or interrupt will
occur any time the watchdog is running and has an operating clock source"
(p. 150).

- In **Sleep** the ILRC is on (p. 78), so the WDT keeps counting; whatever
  wakes the core must keep feeding it as today.
- In **Deep-sleep** the ILRC stays on whenever the RTC uses it, which is
  how this board's clock works. **Inferred:** a running WDT then keeps
  counting and **resets the board about 11-12 s into Deep-sleep**. Either
  stop it (`WDT_CFG.WDTEN = 0` with key `0x5AFA`; the manual shows no
  lock-once-started, and `watchdog_stop()` already does this,
  `kb/watchdog.c`), or wake on the RTC at an interval shorter than the
  timeout to feed it.
- **Silent:** whether the WDT runs in Deep-sleep at all. **Measured on this
  board: it does not.** On 10-18 a 30 s sleep unfed gave no reset; on 10-28
  three more ran to their caps, 120, 120 and 600 counted seconds, with the
  ILRC kept on by the RTC (`history/wdt-asleep-20261028-2330/`). The
  inference above is wrong for Deep-sleep.

### Light sleep on this board

The plan is in [`../plans/BATTERY-GAUGE-PLAN.md`](../plans/BATTERY-GAUGE-PLAN.md),
"A light sleep rung". What the manual adds:

- PMU Sleep keeps every timer running, so the row ISR (CT16B1) and the GPT
  (CT16B3) wake the core on schedule. **The core always has a waker** while
  either runs (p. 74).
- The current idle hooks already write `PMU_CTRL = 4` on idle entry and `0`
  on exit (`qmk/platforms/chibios/boards/SN_SN32F290/configs/chconf.h:30-38`).
  With `CORTEX_ENABLE_WFI_IDLE FALSE` (`kb/config.h:244`) no `WFI` follows,
  so those writes do nothing today. Turning WFI back on turns PMU Sleep on,
  with the USB question above.
- Slowing the clock (48 → 12 MHz IHRC, 2.9 mA against 11 mA at 3.3 V,
  p. 263) breaks USB (it needs the 48 MHz PLL, p. 19) and changes every
  HCLK-derived rate (UART2 baud, PWM, the 187.5 kHz ST counter, SPI). It
  also needs `FLASH_LPCTRL = 0` (p. 255). Battery-only, and all of it
  re-derived, or not at all.
- The ADC's ~100 µA (p. 264) is worth turning off between the 10 Hz
  samples: re-enable, wait 100 µs (p. 96), convert.

### Deep-sleep on this board: wake on keypress

**Inferred design facts**, from the manual and the firmware's matrix
scheme, written before anything was tried. **Since tried and built:** the
experiment of 10-18/19 (247 of 247 key wakes, 3.24 mA asleep, the watchdog
not counting in Deep-sleep, the RTC's second ~13% slow) and the deep-sleep
build; what the firmware does now is in [hardware.md](hardware.md), "Deep
sleep".

- **The matrix is COL2ROW**: the six key rows (`B14 B15 B19 D19 A19 A18`)
  are driven, low to select and high when unselected
  (`MATRIX_UNSELECT_DRIVE_HIGH`, `kb/config.h:145`). The 15 shared columns
  are read as pull-up inputs (`qmk/quantum/matrix.c:136-160`). So a wake
  configuration is: **all six rows driven low, all 15 columns pull-up
  inputs with edge interrupts**. A press pulls its column low.
- The columns sit on **P0.4-P0.7** (IRQ31) and **P2.0-P2.9, P2.14**
  (IRQ29). Every one has an internal pull-up (p. 37). Set `IBS` (both
  edges) as the manual recommends; a key held at sleep entry then wakes on
  release.
- **The LED rows must be low** (NPN off) and the column PWM outputs off
  (`PWMxIOEN = 0`), or the transistors conduct. The columns double as the
  LED PNP drivers; how much current a held key draws through that path
  depends on the board's transistor network.
  `../ajazz-ak820-pro/docs/matrix.md` sketches one (a PNP base through
  1 kΩ and a diode per column), but **its diode orientation contradicts the
  working COL2ROW firmware**, so measure rather than trust it.
- The knob: encoder A is `B2` (P1.2, IRQ30), B is `A10` (P0.10, IRQ31); its
  push is matrix key [0][14]. The mode slider (`B1`, `B12`, `B13`) needs no
  wake, because a flip reboots the board anyway ([hardware.md](hardware.md)).
- **The CH582F link.** UART2 stops in Deep-sleep, so a frame arriving
  while asleep is lost. P1.6 (URXD2) could be an edge wake source, but
  **Silent:** whether a pin's GPIO edge detector still works while a
  peripheral owns the pin. The first byte is lost either way.
- **ChibiOS's PAL interrupt handler loses edges.** It reads `RIS` and then
  writes `IC = 0xFFFFFFFF` (`contrib/hal/ports/SN32/LLD/SN32F2xx/GPIO/hal_pal_lld.c:84-88`).
  That is the same pattern as the SPI0 lost-completion bug
  ([section 9](#spi0-dma-the-lcd-blit)): an edge latched between the two
  instructions is cleared unseen. A wake handler should clear only the
  bits it read. PAL callbacks are off on this board
  (`PAL_USE_CALLBACKS FALSE`), so a wake path writes its own handler anyway.
- Deep-sleep stops the RGB row ISR, and with it key scanning. The waking key
  is still down when scanning resumes, so it types, provided the clocks are
  restored within a few ms (the wake itself takes ~13 µs, plus the PLL's
  100 µs).
- **VREG33 / VDDIO1 in Deep-sleep: Silent, and the riskiest unknown.**
  VDDIO1 (pin 57) powers the LCD and the SPI flash
  (`../ajazz-ak820-pro/README.md`, "MCU-Flash Module wiring", "LCD Module
  wiring"). Where VDDIO1 comes from is not documented; VREG33 (pin 35) is
  the USB block's 3.3 V regulator, and **USB is "Disable" in Deep-sleep**
  (p. 78). If VDDIO1 is fed from VREG33, Deep-sleep may brown out the panel
  and the flash, or (if `VREG33_EN` were cleared, see
  [USB](#usb-full-speed-device-base-0x4005_c000-p-237-250)) push VDD onto the
  3.3 V rail. **Measure pin 35 and pin 57 in Deep-sleep before trusting
  either.**

## 5. Interrupts

**NVIC:** 32 external IRQs, `IPRn` at `0xE000_E400 + 4n`, **only bits 7:6
of each priority byte are implemented**: four levels, 0 highest. Writing 255
stores 192 (p. 45-46). Use word access (Cortex-M0). `ISER` `0xE000_E100`,
`ICER` `0xE000_E180`, `ISPR` `0xE000_E200`, `ICPR` `0xE000_E280` (p. 44-45).

The vector table (p. 43-44). Exceptions: Reset 1, NMI 2, HardFault 3,
SVCall 11, PendSV 14, SysTick 15. IRQn = vector − 16; the table offset is
`0x40 + 4 × IRQn`, which is ChibiOS's `VectorNN` name. The IRQs this board
uses, and the ones a wake path will:

| IRQ | Vector | Source | Board use and priority (`kb/mcuconf.h:77-88`, driver defaults) |
|---|---|---|---|
| 1 | `Vector44` | USB | QMK USB, priority 1 (ChibiOS default) |
| 6 | `Vector58` | SPI0 | LCD FIFO and the flash→LCD DMA completions, priority 3 |
| 7 | `Vector5C` | SPI1 | external flash reads, priority 3; vector disabled during a DMA |
| 8 | `Vector60` | UART2 | CH582F link, **priority 1** |
| 15 | `Vector7C` | CT16B0 | RGB PWM (no callback), priority 3 |
| 16 | `Vector80` | CT16B1 | **the RGB row ISR** (period callback, also scans the keys), priority 3 |
| 17 | `Vector84` | CT16B2 | RGB PWM (no callback), priority 3 |
| 19 | `Vector8C` | CT16B3 | 20 kHz GPT tick (backlight and indicator PWM), **priority 2** |
| 21 | `Vector94` | CT16B5 | ChibiOS time counter; no interrupt used |
| 23 | `Vector9C` | RTC | the 1 Hz second tick (`rtc.c`), priority 3 |
| 25 | `VectorA4` | WDT | unused (reset mode) |
| 26 | `VectorA8` | LVD | unused |
| 28-31 | `VectorB0`-`BC` | GPIO P3, P2, P1, P0 | unused today; the Deep-sleep wake path |
| 3, 4 | | I2S0, I2S1 | unused; pended on purpose by the `HC_FAULT` test (`kb/hid_protocol.c:885-891`) |

The manual also lists `CMP3` at IRQ5 (p. 43) on a part with three
comparators (CMP0-2).

**Our priority table and why:** [leds.md](leds.md), "Interrupt priority
ordering". Two facts from this chapter belong next to it:

- With two priority bits, equal priorities never pre-empt each other
  (Cortex-M0). That is why SPI0 at priority 3 waits out a ~188 µs row ISR,
  the timing that exposed the 660-byte lost completion ([display.md](display.md)).
- **Inferred, unverified:** `SN32_ST_IRQ_PRIORITY` defaults to **8**
  (`contrib/hal/ports/SN32/LLD/SN32F2xx/SysTick/hal_st_lld.h:49`). ChibiOS
  writes it as `8 << 6`, shifted to bit 24 of `SHPR3`
  (`qmk/lib/chibios/os/hal/ports/common/ARMCMx/nvic.c:147-157`), which
  overflows 32 bits to **0, the highest priority**. If so, SysTick (the
  tick-less alarm) out-ranks UART2. Read `SCB->SHPR[1]` on the board to
  confirm.

ChibiOS on ARMv6-M masks interrupts with `PRIMASK` (`chSysLock()` is
`cpsid i`), so **every critical section delays every interrupt, UART2
included**: the ADC read (~11 µs, `kb/battery.c:108-120`), the bit-banged
I2C (~1 ms per byte, `kb/rules.mk:14-18`), and the flash program windows
([section 10](#10-internal-flash-controller)).

**AIRCR** `0xE000_ED0C`: write `0x05FA` to `VECTKEY[31:16]` with
`SYSRESETREQ` b2 for a software reset (p. 46).

## 6. GPIO and pin functions

Four ports, P0-P3, pins 0-19 (P2 has 0-15, P3 lacks 3-4) (p. 18, 81).
**Everything resets to a floating input with the Schmitt trigger on**
(`CFG = 0xAAAAAAAA`, `MODE = 0`, p. 80-81).

| Offset | Register | Function (p. 81-85) |
|---|---|---|
| `0x00` | `DATA[19:0]` | read: pin levels; write: output latch |
| `0x04` | `MODE[19:0]` | 0 input, 1 output. A peripheral or the ADC takes the pin over "directly, not through GPIOn_MODE" (p. 81) |
| `0x08` | `CFG` | 2 bits per pin 0-15, see below |
| `0x0C` | `IS` | 0 edge, 1 "event" (= level) sensitive |
| `0x10` | `IBS` | 1: both edges (overrides `IEV`) |
| `0x14` | `IEV` | 0 rising or high, 1 falling or low |
| `0x18` | `IE` | per-pin interrupt enable; only enabled pins reach the NVIC (p. 84) |
| `0x1C` | `RIS` | raw flags, read-only |
| `0x20` | `IC` | write 1 to clear a flag |
| `0x24`/`0x28` | `BSET`/`BCLR` | atomic set or clear (ChibiOS `palSetPad`/`palClearPad` use these) |
| `0x30` | `CFG1` | `CFG` for pins 16-19 (P0, P1, P3) |

`CFG` encoding per pin (p. 81-85):

| Value | Meaning |
|---|---|
| `00` | pull-up on |
| `01` | **pull-down**, but only on P3.10-P3.13; reserved elsewhere |
| `10` | no pull, Schmitt trigger on (reset) |
| `11` | no pull, Schmitt trigger off, data held low (for analog pins) |

**Per-pin limits** (p. 16, 37-38; the p. 37 table read back by position):

- **Pull-ups** (75 kΩ typical at 3.3 V, 50 kΩ at 5 V, p. 263) on every pin
  **except P0.19**. **Conflict:** `CFG1` offers a pull-up for P0.19
  (p. 85). **Board:** P0.19 is key row R4 (`A19`), always driven, so
  nothing relies on it.
- **Pull-downs** only on P3.10-P3.13 (and P3.6, SWCLK's debug pull-down,
  p. 259). P3.10-P3.13 are RGB rows here, so the key matrix has no
  pull-down to use.
- **No GPIO open-drain mode.** The "open-drain" column of p. 37 marks only
  the I2C-capable pins (P0.1, 0.2, 0.6, 0.7, 0.10, 0.11, P1.1, 1.2, 1.4,
  1.5, 1.8-1.11, 1.13, 1.14), and the I2C peripheral drives them open-drain
  itself (p. 168). **Board:** P0.14/P0.15 (the PCF8563 bus) are not among
  them, so the bit-banged I2C emulates open-drain by switching direction
  (`SW_I2C_USE_OPENDRAIN FALSE`, `kb/halconf.h:15-22`).
- **High-sink pins**: P0.0-P0.3, P1.12, P1.13 sink 80-100 mA at
  VSS + 1.5 V; every other pin 12-20 mA source or sink at 0.5 V from the
  rail (p. 16, 264). **Board:** P1.12/P1.13 are the slider; P0.0-P0.3 are
  free.
- The SWD pins carry internal pulls: SWDIO pull-up, SWCLK pull-down (p. 259).

**Interrupts.** Edge or level per pin, any pin, one NVIC line per port
(p. 80, 83-84). Only edges wake from Deep-sleep (p. 75). The ChibiOS
handler's read-then-clear-all race is described in
[section 4](#deep-sleep-on-this-board-wake-on-keypress).

### Voltage domains: VDD and VDDIO1

Most pins run at VDD. A group runs at **VDDIO1** (pin 57, 1.8 V to VDD,
"shall not be floating", p. 26, 263). **Conflict, on which pins:** P0.12-P0.15,
P1.6-P1.11, P3.0-P3.2, P3.5-P3.6 (p. 26, 263); P3.0-P3.6 instead of
P3.0-P3.2/P3.5-P3.6 (p. 17); P1.6-P1.15 and P3.0-P3.9 (p. 33). Take the
majority reading (p. 26 and p. 263).

**Board:** every 3.3 V signal sits in that group: the LCD's SPI0 (P3.0,
P3.2, CS P1.8), the flash's SPI1 (P0.12, P0.13, P1.10, P1.11), the CH582F's
UART2 (P1.6, P1.7) and the PCF8563 (P0.14, P0.15). VDDIO1 is wired to the
LCD's and the flash's supply (`../ajazz-ak820-pro/README.md`). The LCD's
`DC` (P3.14) and `RST` (P0.17) are outside the group, and reach the panel
through a Schottky diode with a 10 kΩ pull-up, a level shift from the
4-4.8 V VDD (same README). **Silent:** whether VDDIO1 is fed from VREG33;
see [section 4](#deep-sleep-on-this-board-wake-on-keypress).

## 7. Timers CT16B0-CT16B5

Six 16-bit up-counters, each with an 8-bit prescaler, one capture input, and
match registers that can interrupt, reset or stop the counter and drive
PWM pins (p. 114).

| Timer | Clock | Counting | PWM outputs | Period register | Board use |
|---|---|---|---|---|---|
| CT16B0 | HCLK or PLL_VCO | up, down, center | 4 (+4 inverted with dead-band) | MR9 | RGB columns |
| CT16B1 | HCLK or PLL_VCO | up | **12** | MR12 | RGB columns + **the row ISR** |
| CT16B2 | HCLK or PLL_VCO | up, down, center | 4 | MR9 | RGB columns |
| CT16B3 | HCLK or PLL_VCO | up | 2 (+2 inverted) | MR9 | **20 kHz GPT tick** |
| CT16B4 | HCLK or PLL_VCO | up | 2 (+2 inverted) | MR9 | free |
| CT16B5 | HCLK, PLL_VCO or **ELS** | up, down, center | 4 | MR9 | **ChibiOS system time** |

PCLK is up to 96 MHz (PLL_VCO) (p. 114, 124-125).

### Registers (p. 123-149)

| Offset | Register | Notes |
|---|---|---|
| `0x00` | `TMRCTRL` | `CEN` b0 (**set it last**), `CRST` b1 (synchronous reset of TC and PC, self-clearing), `CLKSEL` b2 (B5: bits 3:2), `CM[6:4]` counting mode (B0/B2/B5) |
| `0x04` | `TC` | the 16-bit counter, **R/W**. Wraps `0xFFFF` → 0 with no interrupt |
| `0x08` | `PRE` | prescale: TC advances every PR+1 PCLKs. **Conflict:** documented as `PR[15:0]` while the prescale counter `PC` is 8-bit and the features say an 8-bit prescaler; ChibiOS's ST refuses PRE > 255 |
| `0x0C` | `PC` | prescale counter |
| `0x10` | `CNTCTRL` | timer or counter (count CAP0 edges) |
| `0x14` | `MCTRL` | per match: `MRnIE`, `MRnRST`, `MRnSTOP` (three bits each); for B0/B2/B3/B4/B5 the MR9 trio is at bits 21-23 |
| `0x18` | `MCTRL2` | CT16B1's MR10-MR12 |
| `0x20`-`0x50` | `MR0`..`MR12` | match values (B0/B2/B5: MR0-3 and MR9; B3/B4: MR0-1 and MR9; B1: MR0-12) |
| `0x84`/`0x88` | `CAPCTRL`/`CAP0` | capture |
| `0x8C`/`0x90` | `EM`/`EMC` | match-output pin action (nothing, low, high, toggle) |
| `0x98` | `PWMCTRL` | B0/B2/B3/B4/B5: `PWMnEN`, `PWMnMODE`, `PWMnIOEN` all here. CT16B1 splits them into `PWMCTRL` (modes), `PWMENB` (`0xA0`) and `PWMIOENB` (`0xA4`) |
| `0xA8`/`0xAC` | `RIS`/`IC` | raw flags; write 1 to clear |
| `0xB0`.. | `PWMmNIOCTRL`, `PWMmNDB` | inverted outputs and dead-band (B0, B3, B4) |

**The write key.** On CT16B0, B2, B3, B4 and B5, writes to `MCTRL`, `MRn`,
`EM`, `PWMCTRL`, `PWMmNIOCTRL` and `PWMmNDB` are **ignored unless bits 31:24
carry `0x5A`** (p. 126-149). CT16B1 has no key. **Board:** this is the
"`MCTRL` gotcha" in [leds.md](leds.md): `indicators.c` must write
`CT16_PWM_UNLOCK(...)` to set `MR0RST` on CT16B3
(`kb/indicators.c:158-174`). (`PWMCTRL` for B3/B4 shows the key at bits
31:22, a typo, p. 140.)

**There is no interrupt-enable register.** The enables are the `MRnIE` bits
in `MCTRL` and `CAP0IE` in `CAPCTRL`. `RIS`'s caption mentions a
"CT16Bn_IE", which does not exist (p. 144).

### PWM behaviour (p. 118-122)

- **Mode 1:** the output is 0 while TC < MRn and goes high at the match.
  **Mode 2** is the inverse. Codes `10`/`11` force the output to 0 or 1.
- The cycle length is the match register with `MRnRST` set; every other
  PWM match must have `RST` and `STOP` clear (p. 118).
- A match equal to the cycle length gives a one-tick pulse; a match of 0
  gives a constant level.
- A match interrupt is raised "in the next clock after the timer reached
  the match value" (p. 116).

### How this board uses them

- **RGB (CT16B0/B1/B2):** 15 columns spread over the three timers
  (`kb/config.h:19-26`), period `RGB_MATRIX_MAXIMUM_BRIGHTNESS + 1 = 256`
  ticks (`qmk/drivers/led/sn32f2xx.c:127`), PWM clock 4.8 MHz (PRE 9).
  - The row ISR is CT16B1's period callback.
  - **It re-arms all three counters at its END** by writing `TC = 0xFFFF`
    (`qmk/drivers/led/sn32f2xx.c:737-745`), so the next cycle starts one tick
    later. The period is therefore the ISR's own duration plus about
    50-70 µs, not 256 ticks. That is why it measures 3,876/s instead of
    18,750/s ([leds.md](leds.md), "CPU budget"; [hardware.md](hardware.md)).
    The manual allows it: TC is read-write (p. 125).
- **GPT (CT16B3, `GPTD4`):** 1 MHz timebase (PRE 47), MR0 = 50, 20 kHz,
  priority 2. The ChibiOS GPT LLD never sets `MR0RST`, so without the
  board's fix the counter runs the full 16 bits and the callback fires once
  per wrap, 15 Hz instead of 20 kHz (`kb/indicators.c:132-174`;
  [leds.md](leds.md), "The 20 kHz GPT tick").
- **CT16B4:** free.

### CT16B5: ChibiOS's system timer

`SN32_ST_USE_TIMER SN32_TIM_CT16B5` (`kb/mcuconf.h:31-32`) frees CT16B0 for
PWM. ChibiOS runs **tick-less** (`CH_CFG_ST_TIMEDELTA 2`):

- the time base is CT16B5 free-running at HCLK/256 = **187,500 Hz**, 16-bit
  (`qmk/platforms/chibios/boards/SN_SN32F290/configs/chconf.h:24-26`;
  `contrib/hal/ports/SN32/LLD/SN32F2xx/SysTick/hal_st_lld.c:136-160`);
- the alarm is the Cortex **SysTick**.

Both stop in Deep-sleep; SysTick in Sleep is **Silent**
([section 4](#sleep-in-detail-p-74-76)).

**SysTick** itself (p. 40-42): 24-bit, clock fixed to the system clock
(`CLKSOURCE` reads 1). `SYST_CALIB.TENMS` reads `0xA71FF`, which matches no
clock this part runs at; ignore it.

## 8. Watchdog

| Item | Fact |
|---|---|
| Base | `0x4001_0000` (p. 152) |
| Clock | **ILRC** through `SYS1_APBCP1.WDTPRE[22:20]`: `000`=/1, `001`=/2, `010`=/4, `011`=/8, `100`=/16, `101`=/32 (p. 71, 150). Reset the WDT with `SYS1_PRST.WDTRST` after changing it (p. 71) |
| Counter | a fixed /128 prescaler, then an 8-bit down-counter reloaded from `TC + 1` (1..256) (p. 150, 152) |
| Timeout | (`TC` + 1) × 128 × `WDTPRE` divider / f_ILRC |
| `WDT_CFG` `0x00` | `WDTEN` b0, `WDTIE` b1 (0: reset mode, 1: interrupt mode), `WDTINT` b2 (flag; feed before clearing). Key **`0x5AFA`** in bits 31:16 on every write (p. 152) |
| `WDT_TC` `0x08` | `TC[7:0]`, reset `0xFF`, same key |
| `WDT_FEED` `0x0C` | write `0x55AA` with the key to reload (p. 153) |
| Start sequence | prescaler, then `TC`, then `CFG` (p. 150) |
| Stoppable? | yes: `WDTEN` is read-write and no lock is described |
| Low power | counts whenever it has a clock (p. 150): in Sleep, and in Deep-sleep while the RTC keeps the ILRC on (Inferred; see [section 4](#the-watchdog-and-low-power)) |

**Board** (`kb/watchdog.c:39-40, 89-103`): `WDTPRE = 4` and `TC = 188`.

- **The manual confirms `4` is /16** (p. 71). The source comment calls that
  encoding "assumed, not datasheet-confirmed" because the table did not
  survive an earlier text extraction; it is settled now.
- Timeout = 189 × 128 × 16 / f_ILRC: **12.1 s at 32 kHz, 11.5 s at this
  unit's ~33.6 kHz, 10.6 s at the 36.5 kHz the p. 265 graph gives for
  25 °C**. The ILRC's temperature curve moves it about ±15% over the
  operating range.
- [hardware.md](hardware.md) records a wedge recovering in ~12.3 s.
- `bootloader_jump()` stops the WDT before the reset (`kb/watchdog.c:126`).
  **Inferred:** a software reset restores `WDT_CFG` to its reset value
  (disabled), because "all system registers" return to initial values on
  reset (p. 49-50), so the stop is belt and braces.

The manual's advice not to feed from an interrupt handler (p. 50) is
followed: `watchdog_kick()` runs at the end of the main loop's housekeeping.
A flash write or erase should be preceded by a feed (p. 251).

## 9. RTC, SPI and its DMA, UART, I2C, USB, ADC

### RTC (base `0x4001_2000`, p. 154-157)

The "RTC" is only a prescaler with a seconds interrupt: a 20-bit reload, a
counter, and one interrupt. **Conflict:** the features promise a 32-bit
counter and "three dedicated interrupt lines" (p. 154); the registers give
one interrupt (`SECIF`) and a counter that runs 0..`SECCNTV`, then wraps,
raising `SECIF` at the match (figure, p. 154).

| Offset | Register | Facts |
|---|---|---|
| `0x00` | `CTRL` | `RTCEN` b0; **set last**; enabling resets the counter |
| `0x04` | `CLKS` | `CLKSEL` b0: 0 ILRC, 1 ELS. Change only with `RTCEN = 0`; a change resets the counters |
| `0x08`/`0x0C`/`0x10` | `IE`/`RIS`/`IC` | `SECIE`, `SECIF`, `SECIC` |
| `0x14` | `SECCNTV[19:0]` | reload, reset `0x8000`; **writing it resets `SECCNT`**; 0 is replaced by `0x8000` |
| `0x18` | `SECCNT` | the counter (read-only) |

- The RTC registers are "reset by cold boot" (p. 154). **Silent:** whether
  they survive a warm reset; ChibiOS re-initializes them at every boot
  anyway.
- The RTC keeps running in Deep-sleep and is a wake source (p. 76-78).

**Board** ([clock.md](clock.md)): `CLKSEL = 0` (ILRC, no crystal). The
period is `SECCNTV + 1` counts per second (`kb/rtc/rtc.c:214`), seeded at
33600 (`kb/config.h:340`).

- The reset-on-write behaviour (p. 157) is why every steady-state
  `SECCNTV` write happens in the tick ISR at the match
  ([clock.md](clock.md), "Reload ownership").
- **The ILRC is not trimmed; the RTC period is.** No ILRC trim register
  exists. "Disciplining the ILRC" in our docs means adjusting `SECCNTV` from
  the USB SOF count (`SN_USB->FRMNO`, `kb/rtc/rtc.c:535`) or from the
  PCF8563.

### SPI0 and SPI1 (p. 158-167)

Motorola SPI, master or slave, 4-16-bit frames, 8-frame TX and RX FIFOs,
MSB or LSB first, up to **36 Mbps master** (p. 158). The timing table says
`tSCK ≥ 33 ns`, about 30 MHz (p. 161).

| Offset | Register | What matters |
|---|---|---|
| `0x00` | `CTRL0` | `SPIEN` b0, `LOOPBACK` b1, `SDODIS` b2, `MS` b3 (0 master), `FRESET[7:6]` (`11` resets the FSM and FIFOs, self-clearing), `DL[11:8]` (length − 1), `TXFIFOTH[14:12]`, `RXFIFOTH[17:15]`, `SELDIS` b18 (reset 1: auto-SEL off). After any change while enabled, reset with `FRESET` (p. 162) |
| `0x04` | `CTRL1` | `MLSB` b0, `CPOL` b1, `CPHA` b2 |
| `0x08` | `CLKDIV` | SCK = PCLK / (2 × `DIV` + 2) |
| `0x0C` | `STAT` | `TX_EMPTY` b0, `TX_FULL` b1, `RX_EMPTY` b2, `RX_FULL` b3, `BUSY` b4, `TXFIFOTHF` b5, `RXFIFOTHF` b6 |
| `0x10` | `IE` | `RXOVFIE` b0, `RXTOIE` b1, `RXFIFOTHIE` b2, `TXFIFOTHIE` b3, `DMAHTIE` b4, `DMATCIE` b5 (DMA bits on SPI0 only) |
| `0x14` | `RIS` | the same bits as flags; RX time-out is 32 PCLKs |
| `0x18` | `IC` | write 1 to clear |
| `0x1C` | `DATA` | FIFO |
| `0x20` | `DF` | "data fetch": enable when SCK > 6 MHz (p. 166). ChibiOS calls it `DFDLY.DFETCH_EN` |
| `0x24` | `DMACTRL` | SPI0 only: `DMAEN` b0 (cleared by hardware), `DIR` b1 (0: SPI1 RX → SPI0 TX; 1: SPI0 RX → SPI1 TX) |
| `0x28` | `DMACNT[27:0]` | SPI0 only: transfer count |
| `0x2C` | `DMAHTCNT[27:0]` | SPI0 only: half-transfer point (reset `0xFFFFFFF`) |
| `0x30` | `CURCNT[27:0]` | SPI0 only: "counts from 0 to DMACNT" |

**Board:** both run 8-bit, mode 0, `CLKDIV 0`: **24 MHz** from a 48 MHz
PCLK (`kb/graphics/lcd_bus.c:88-92`). Chip selects are GPIOs (P1.8 panel,
P0.13 flash) because a DMA frame must hold CS low throughout.

### SPI0 DMA: the LCD blit

The only DMA on the chip. It moves bytes from one SPI's RX FIFO to the
other's TX FIFO, here **external flash (SPI1) → LCD (SPI0)**, "without any
CPU actions" (p. 166, 224). The DMA data length is 8 bits on the SPI side
(p. 166); our driver switches SPI0 to 16-bit frames for the pixel stream
(`DL = 0xF`). The sequence lives in
`contrib/hal/ports/SN32/LLD/SN32F2xx/SPI/hal_spi_v2_lld.c:180-215`:

1. `DMAEN = 0`, `DIR = 0`, `DMACNT = len − 1`, `DMAHTCNT = (len − 1) / 2`.
2. Clear the flags, enable `DMATCIE | DMAHTIE`, then `DMAEN = 1`.
3. Completion arrives on the SPI0 vector.

Board facts the manual gets wrong or leaves out:

- **`DMACNT` never counts down.** **Conflict:** the manual says that once
  enabled it is "read-only, indicating the remaining bytes" (p. 166). On
  this board it holds the programmed value. Progress is `CURCNT`, which
  keeps the *previous* transfer's final count until the next transfer
  starts, then runs 0..`DMACNT`; the hardware clears `DMAEN` at completion
  ([display.md](display.md), "Blit timeouts"; `kb/graphics/lcd_bus.c:888-910`).
- **The count is N − 1.** The SPI chapter only says "number of data"
  (p. 166). The EBI chapter's twin registers say "(CNT+1) bytes" (p. 233),
  which is what our code does.
- **Never write `IC` wider than the flags you just read.** A completion
  latched between reading `RIS` and writing `IC = 0x3F` was wiped unseen,
  and the `IC` write also drops the pending request. That was the "lost
  completion" fixed in ChibiOS `c57623d0d2`. The handler now clears only
  what it read, then re-checks `RIS` and `DMAEN`
  (`hal_spi_v2_lld.c:268-292`; [display.md](display.md)). **Silent:** the
  manual says nothing about a clear racing a flag.
- **SPI1's `RXFIFOTHIE` gates the DMA request.** Masking it stalls the
  transfer, so the driver disables SPI1's *NVIC vector* for the transfer
  instead (`hal_spi_v2_lld.c:148-156`). **Silent:** the manual never names
  the DMA request source.
- **The DMA needs the EBI and LCD clocks on** (`kb/graphics/lcd_bus.c:104`).
  **Silent.**
- `DMAHTCNT`'s description says the half-transfer "triggers the DMATC
  interrupt" (p. 167); it means `DMAHT`.

### UART (UART2 = the CH582F link; p. 176-188)

A 16550-style UART at `0x4005_4000` (UART2):

| Offset | Register | Notes |
|---|---|---|
| `0x00` | `RB`/`TH`/`DLL` | depends on `DLAB` |
| `0x04` | `IE`/`DLM` | |
| `0x08` | `II`/`FIFOCTRL` | `FIFOEN` must be 1; the RX trigger supports only "1 character" |
| `0x0C` | `LC` | `DLAB` b7 |
| `0x14` | `LS` | `RDR`, `OE`, `PE`, `FE`, `BI`, `THRE`, `TEMT`, `RXFE` |
| `0x28` | `FD` | `DIVADDVAL[3:0]`, `MULVAL[7:4]` (+1), `OVER8` b8 |
| `0x30` | `CTRL` | `UARTEN` b0, `MODE[3:1]` (000 UART), `RXEN` b6 and `TXEN` b7 (both reset 1) |
| `0x34` | `HDEN` | half duplex |

- Baud = PCLK / (oversampling × (256·DLM + DLL) × (1 + DIVADDVAL/MULVAL)),
  oversampling 8 or 16 (p. 178).
- Rules: 1 ≤ MULVAL ≤ 15, DIVADDVAL < MULVAL, MULVAL − DIVADDVAL ≠ 2; with
  the fractional divider active and DLM = 0, DLL ≥ 3 (p. 178, 187).
- Read `LS` before `RB` so the error bits match the byte (p. 182).
- **Silent: the FIFO depth.** It is never stated. `kb/config.h:76-92`
  reasons about "the FIFO depth" as UART2's real budget; that number is
  unknown.

**Board:** 115200 8N1, oversampling 16, PCLK = HCLK
(`kb/bluetooth/ch582f_ajazz.c:369-378`;
`contrib/hal/ports/SN32/LLD/SN32F2xx/UART/hal_serial_lld.c:175-205`), on
P1.7 TX / P1.6 RX at priority 1. A byte lasts 87 µs. UART2 has no wake
function of its own ([section 4](#deep-sleep-on-this-board-wake-on-keypress)).

### I2C (p. 168-175)

Two controllers, 100 and 400 kHz, master or slave, open-drain outputs, an
SCL-low time-out (`TO × 32` PCLKs), bit rate = PCLK / (`SCLHT` + `SCLLT`)
(p. 175). **Board:** unused. The PCF8563 is on P0.14 (SCL) / P0.15 (SDA),
which the I2C peripheral cannot reach ([section 6](#pfpa-the-pin-mux-base-0x4004_2000-p-86-94)),
so ChibiOS's software I2C bit-bangs it with interrupts masked, ~1 ms per
byte (`kb/rules.mk:14-18`, `kb/rtc/rtc.c:20-24`).

### USB full-speed device (base `0x4005_C000`, p. 237-250)

- One device address, EP0 (8-64 B), and **6** INT/BULK endpoints (p. 17,
  237). **Conflict:** item 4 on p. 237 says 4.
- 512 B of endpoint SRAM at base + `0x100`; buffer offsets word-aligned
  (p. 238).
- Internal D+ 1.5 kΩ pull-up powered by the on-chip 3.3 V regulator
  (VREG33, pin 35, 3.0-3.4 V when VCC ≥ 3.6 V, 60 mA, p. 17, 265).
- Needs the 48 MHz PLL (p. 19).

`USB_CFG` (`0x10`, p. 245):

| Bit | Name | Meaning |
|---|---|---|
| 31 | `VREG33_EN` | VREG33 on. **"If VREG33 is disabled, the VREG33 will be switched to IC_VDD"**: clearing it would put VDD (up to 4.8 V here) on pin 35 |
| 30 | `PHY_EN` | transceiver; **auto-disabled entering Sleep or Deep-sleep** |
| 29 | `DPPU_EN` | D+ pull-up |
| 28 | `SIE_EN` | |
| 27 | `ESD_EN` | |
| 26 | `DIS_PDEN` | 175 kΩ pull-downs |
| 5:0 | `EPn_DIR` | endpoint directions |

**Conflict:** the register summary gives `USB_CFG` a reset value of
`0x8000_0000` (p. 241); its own header says `0x0000_0000` (p. 245), while
its bit table gives `VREG33_EN` a reset of 1.

Interrupts:

- `INTEN` (`0x00`): `BUS_IE` (reset, suspend, resume), `USB_SOF_IE`,
  `USB_IE`, `BUSWK_IE`, per-endpoint ACK/NAK enables.
- `INSTS` (`0x04`) and `INSTSC` (`0x08`, write 1 to clear): `BUS_RESET`
  (SE0 > 2.5 µs), `BUS_SUSPEND` (idle > 3 ms), `BUS_RESUME`, `USB_SOF`,
  `BUS_WAKEUP` ("wakeup from suspend mode under USB PLL 48MHz is off"), and
  the EP0 and endpoint flags (p. 241-244).
- `FRMNO` (`0x60`) is the 11-bit SOF frame number. `PHYPRM` (`0x64`): the
  manual suggests 0x20 in bits 31:26, i.e. the `0x8000_0000` ChibiOS writes;
  ChibiOS's `PHYPRM2 = 0x4004` is undocumented.
- `SGCTL` (`0x14`) drives the bus by hand (`BUS_DRVEN`, `BUS_DP`,
  `BUS_DN`), used for remote wake-up K-state.

**Board** (`contrib/hal/ports/SN32/LLD/SN32F2xx/USB/hal_usb_lld.c:233-254, 450-490`):
the driver clears `PHY_EN | ESD_EN` on `BUS_SUSPEND` and restores them on
resume or wake-up. Remote wake-up is the board's own `usb_wakeup_try()`
(`kb/ak820pro.c`, `USB_WAKEUP_ON_KEYPRESS`), because
`NO_USB_STARTUP_CHECK` compiles QMK's out (`kb/config.h:181-196`).

### ADC (base `0x4002_6000`, p. 95-101, 264)

- 12-bit SAR. AIN0-AIN15 are **P2.0-P2.15** (P2.0 doubles as the external
  reference input), AIN16 an internal reference, AIN17/AIN18 the op-amp
  outputs.
- `ADC_PCLK` must stay below 16 MHz (p. 96).
- **Wait 100 µs after `ADENB = 1`** before the first conversion (p. 96, 97,
  264).
- Disable it before Sleep or Deep-sleep (p. 96).
- About 100 µA when on (p. 264).

`ADC_ADM` (`0x00`, p. 99-100):

| Bits | Field | Meaning |
|---|---|---|
| 4:0 | `CHS` | channel (16 = AIN16) |
| 5 | `GCHS` | global channel enable |
| 6 | `EOC` | end of conversion |
| 7 | `ADS` | start |
| 8 | `ADLEN` | 1: 12-bit |
| 11:9 | `ADCKS` | ADC_PCLK divider |
| 12 | `ADENB` | ADC on |
| 13 | `AVREFHSEL` | external reference on P2.0 |
| 16:14 | `VHS` | reference choice; `100` = VDD as the high reference with the internal 2.0 V on AIN16 |

- `ADB` (`0x04`) holds the result, unknown after reset. A 12-bit
  conversion is 16 steps of 4 ADC clocks, 64 clocks in all (p. 96, 264).
- **Conflict:** the `ADCKS` encodings in the register (`101` = /16,
  `110` = /32, p. 99) disagree with the conversion table (`100` = /16,
  `101` = /32, p. 96). The board uses `001` (/2), which both agree on.
- With `ADENB` and `GCHS` set, "the ADC shared pins" lose their GPIO
  function and pulls (p. 95, 99). **Inferred:** only the selected channel's
  pin; AIN16 has none.

**Board** (`kb/battery.c:20-60, 98-120`): VDD is measured as
2.0 V × 4096 / code on AIN16 with VDD as the reference (`VHS = 100`), the
manual's own low-battery recipe (p. 95). The internal 2.0 V reference is
1.96-2.04 V (p. 264), so the reading is good to ±2% per part.
`ADC_PCLK` = 48 / 4 = 12 MHz, `ADCKS` /2 → 6 MHz, **10.67 µs** per
conversion (p. 96 table), under `chSysLock()`. `ADENB` stays set
([section 4](#prerequisites-the-manual-imposes-before-either-mode)).

## 10. Internal flash controller

**Organization:** 256 pages of 1 KB (`0x400` each) from `0x0`; the boot ROM
is 4 × 1 KB at `0x1FFF_0000` (p. 251-252). A page is the erase unit.
Erased = all ones (p. 251).

**FMC registers** (base `0x4006_2000`, p. 255-257):

| Offset | Register | Notes |
|---|---|---|
| `0x00` | `LPCTRL` | wait-state mode, key `0x5AFA` ([section 3](#system-clock-switching-sys0-base-0x4006_0000)) |
| `0x04` | `STATUS` | `BUSY` b0; `ERR` b2, write to clear. `ERR` is set by a page-boundary overrun, an illegal address, or programming a location not `0xFFFFFFFF` |
| `0x08` | `CTRL` | `PG` b0, `PER` b1, `MER` b2, `START` b6, `CHK` b7; each cleared by hardware when `BUSY` drops |
| `0x0C` | `DATA` | |
| `0x10` | `ADDR` | **multiple of 8**; set `PG` or `PER` before writing it; writes blocked while `BUSY` |
| `0x14`-`0x1C` | `CHKSUM`, `CHKSUM1`, `CHKSUM2` | hardware checksums of the ROM regions |

**Sequences.**

- Page erase: `PER`, then `ADDR`, then `START`, then wait for `BUSY`
  (p. 254).
- Program: the manual says set `PG`, write the data word to its address,
  wait for `BUSY` (p. 254), and separately that firmware "SHALL fill in more
  or equal to 8 bytes to FLASH_DATA" (p. 254).
- **Conflict:** "programmed 32 bits at a time" (p. 254) against 8-byte
  `ADDR` alignment (p. 256) and a "1-Word (64 bits)" program time (p. 265).
  The working sequence is the LLD's: `PG`, `ADDR`, `DATA` twice (8 bytes),
  `START`, wait (`contrib/hal/ports/SN32/SN32F290/hal_efl_lld.c:278-350`).
- The prose's "PGERR" bit is the register's `ERR`.

**Timing and current** (p. 264-265):

| Operation | Time | Current |
|---|---|---|
| 64-bit program | 10 µs typ, 20 µs max | 3-5 mA |
| page erase | 1 ms typ, 2 ms max | 3-5 mA |
| mass erase | 7-10 ms | |

Endurance is **20,000 cycles minimum**, 100,000 typical. The FMC turns the
IHRC on for every write or erase (p. 251) and clocks itself from it
(p. 252).

**What a write does to the CPU** (p. 251):

- "The MCU is stalled during Flash program and erase operations, although
  peripherals (Timers, WDT, I/O, PWM, etc.) remain active."
- Any read of flash during a write "will stall the bus" until it completes,
  so "code or data fetches cannot be made".
- Feed the WDT first.

**Board** ([leds.md](leds.md), "What an internal-flash write does to the
LEDs"; [battery.md](battery.md), "Internal-flash writes"):

- The LLD runs its program and erase routines from SRAM (`.ramtext`,
  `hal_efl_lld.c:35`).
- It masks interrupts **only across each 8-byte program window**
  (`hal_efl_lld.c:60-61, 336-339`), because an interrupt there fetches its
  vector and handler from the array being programmed, and vectors cannot
  move to SRAM ([section 2](#2-memory-map)). That was a hang on this board.
- **Conflict:** the manual says such a fetch merely stalls and then
  proceeds (p. 251).
- Page erase (1-2 ms) is **not** masked, to spare UART2. **Inferred from
  p. 251:** an interrupt during an erase still cannot run until the erase
  ends, because its vector fetch stalls, so UART2 still waits up to ~2 ms.
  Only the masking is avoided.
- The row ISR blanks every LED row while the flash driver is in its program
  state (`qmk/drivers/led/sn32f2xx.c:702`): the "dark blink" on every
  write.
- `backing_store_pre_write_hook()` drains any flash→LCD DMA before a write
  (`kb/ak820pro.c:669`), the real fix for the 2026-08 hang
  ([hardware.md](hardware.md), "The hang, historically").
- Code security levels CS0-CS2 (p. 253): leaving CS1/CS2 mass-erases the
  user ROM. Never change the code option from firmware.

## 11. Electrical characteristics

**Absolute maximum** (p. 263): VDD −0.3 to **5.5 V**, which is also the
maximum operating voltage (no margin); inputs VSS − 0.2 to VDD + 0.2 V;
−40 to 85 °C operating, −40 to 125 °C storage. ESD: HBM 5 kV, MM 300 V,
CDM 900 V (p. 265).

**Supply current**, typical, the only figures given (p. 263, 265):

| Condition | VDD | Current |
|---|---|---|
| Normal, 12 MHz (IHRC and ILRC on, PLL off) | 3.3 V | 2.9 mA |
| Normal, 24 / 32 / 48 MHz (EHS crystal + PLL, IHRC off) | 3.3 V | 5.9 / 8.5 / **11** mA |
| Normal, USB mode: IHRC 12 MHz / PLL 12 / 24 / 48 MHz | 5 V | 6.3 / 6.5 / 9 / **12** mA |
| Sleep, USB mode, SYSCLK = ILRC 32 kHz, IHRC and PLL off | 5 V | 300 µA |
| **Deep-sleep**, all oscillators and analog off | 3.3 V | **2 µA** |

The conditions: all pins outputs driven low, pull-ups off; LVD and every
peripheral off (notes 1-8). The graph on p. 265 gives about 3 mA at 12 MHz
and 11-11.3 mA at 48 MHz from −40 to 85 °C, and the Deep-sleep curve in
[section 4](#the-modes-p-74-79).

**Board:** **Inferred:** with the RGB and backlight off the board draws
about 107-114 mW ([battery.md](battery.md), "The idle ladder";
[`../plans/current-status.md`](../plans/current-status.md)). The MCU's share
at 48 MHz should be about 11-12 mA × VDD, ~45 mW at 3.9 V, before light
sleep. A measurement of the MCU alone does not exist yet.

**Analog current:** ADC ~100 µA; comparator 75-100 µA each; op-amp
100-150 µA; flash program or erase 3-5 mA (p. 264).

**I/O** (p. 263-264):

| Parameter | Value |
|---|---|
| V_IH / V_IL | 0.7 / 0.3 × VDD. At 3.9 V that is 2.73 / 1.17 V, the threshold that matters for a 3.3 V signal into a VDD-domain pin |
| Pull-up | 40-60 kΩ at 5 V, 50-100 kΩ at 3.3 V |
| Pull-down | the same |
| Source | ≥ 12 mA (20 typ) at VDD − 0.5 V |
| Sink | ≥ 12 mA (20 typ) at VSS + 0.5 V; 80-100 mA at VSS + 1.5 V on P0.0-P0.3, P1.12, P1.13 |

**ADC** (p. 264):

| Parameter | Value |
|---|---|
| Operating supply | 2.5-5.5 V |
| No-missing-code resolution | 10-12 bits (min 10, typ 11) |
| INL, DNL | ±1 LSB |

| Conversion | 64 ADC clocks |

**Misc** (p. 263, 265):

- Power-on ramp ≥ 0.05 V/ms for a clean POR.
- LVD levels as in [section 3](#low-voltage-detector-lvd).
- IHRC and ILRC as in [section 3](#clock-sources).

- The internal core rail (VCORE) is 1.5 V, reset at 1.35 V (p. 16, 264).

## 13. Errata: where the manual and the board disagree

Each item is either a manual inconsistency (with pages) or a board
observation the manual does not predict. Pointers lead to the full story.

**The manual against itself:**

1. ILRC called 16 kHz, 32 kHz and 32.768 kHz (p. 16, 19, 57, 202); the
   graph shows 31-45 kHz with temperature (p. 265).
2. IHRC accuracy ±0.2% (p. 57) against ±2-2.5% (p. 265).
3. Deep-sleep wake sources with and without CT16B5 (p. 76 against p. 77-78).
4. USB "By USBEN" in Sleep (p. 78) against the PHY auto-disabling in Sleep
   (p. 245).
5. The ILRC has no enable (p. 57), yet the user "SHALL decide" whether it
   stays on in Deep-sleep (p. 75).
6. LVD: three levels (p. 16, 265), two register encodings (p. 65);
   inverted enable polarity.
7. Flash programming: 32-bit words (p. 254) against 8-byte lines (p. 254,
   256, 265); "PGERR" against `ERR`.
8. `DMACNT` "remaining bytes" (p. 166) against the board; `DMAHTCNT`
   "triggers DMATC" (p. 167); the N − 1 count stated only for EBI (p. 233).
9. VDDIO1's pin list differs on four pages (p. 17, 26, 33, 263).
10. `USB_CFG` reset value `0x8000_0000` (p. 241) against `0x0000_0000`
    (p. 245).
11. 6 USB endpoints (p. 17) against 4 (p. 237).
12. The bootloader over UART0 (p. 252) against this board's USB bootloader
    (`0C45:7140`).
13. CT16 prescaler 16-bit field against an 8-bit prescaler (p. 125).
14. "CT16Bn_IE" mentioned and absent (p. 144); `PWMKEY` at bits 31:22 for
    B3/B4 (p. 140); `PRST` bit 8 "CT32B0" (p. 73).
15. `PFPA_UART`: `UTXD2` code `10` listed twice (p. 89).
16. `IVTM` "or SRAM" without an encoding (p. 66).
17. RTC: "32-bit counter", "three interrupt lines" against one seconds
    interrupt and a 20-bit reload (p. 154, 157).
18. P0.19 has no pull-up in the pin table (p. 37) but `CFG1` offers one
    (p. 85).
19. `ADCKS` encodings differ between p. 96 and p. 99.
20. `WDTCLKEN = 0` "Reserved" (p. 69) against the WDT clock being gateable
    (p. 150).
21. "Four operating modes", three listed (p. 74).
22. An IRQ for a fourth comparator, CMP3 (p. 43).

**The board against the manual, or where it goes beyond it:**

23. **`DMACNT` never counts down; progress is `CURCNT`**
    ([display.md](display.md); [section 9](#spi0-dma-the-lcd-blit)).
24. **Clearing SPI0 `IC` beyond the flags just read loses a completion,
    and the `IC` write drops the pending request too** (ChibiOS
    `c57623d0d2`; [display.md](display.md)). The same read-then-clear-all
    pattern is still in the PAL GPIO handler
    ([section 4](#deep-sleep-on-this-board-wake-on-keypress)).
25. **SPI1's `RXFIFOTHIE` is the DMA's request gate**; the DMA also needs
    the EBI and LCD clocks (`hal_spi_v2_lld.c:148-156`,
    `kb/graphics/lcd_bus.c:104`).
26. **The row ISR re-arms its counter at its end**, so the timer
    arithmetic overstates the row rate ~4.8× ([leds.md](leds.md),
    [hardware.md](hardware.md)). Manual-consistent (TC is writable) but easy
    to misread.
27. **The ChibiOS GPT needs `MR0RST` set by hand, with the `0x5A` key**
    ([leds.md](leds.md)). The key is in the manual (p. 126-128); the LLD
    misses it.
28. **The ILRC is "disciplined" through the RTC's reload**, from USB SOF or
    the PCF8563 ([clock.md](clock.md)). No ILRC trim exists; ~33.6 kHz on
    this unit, strongly temperature-dependent (p. 265).
29. **`SWRSTF` reads set after POR and after a brownout** (`0x11`, `0x05`;
    [hardware.md](hardware.md)). That matches its reset value of 1 (p. 65),
    but means `SWRSTF` alone proves nothing.
30. **WFI has been off since 2026-08-28** (`kb/config.h:209-244`). It was
    not the fix for the hang, as `config.h` itself records: the fixes were
    the pre-write DMA drain and, for the missed SPI0 completion, ChibiOS
    `c57623d0d2` (2026-09-23). Re-enabling it is open, subject to the
    USB-in-Sleep question (item 4) and a soak
    ([section 4](#light-sleep-on-this-board)).
31. **An interrupt inside a flash program window hung the board**; the
    manual says reads merely stall (p. 251). The LLD masks the program
    windows; erases stay unmasked ([section 10](#10-internal-flash-controller),
    [leds.md](leds.md)).
32. **Every internal-flash write blinks the LEDs dark**, by the row ISR's
    own guard, not by interrupt masking ([leds.md](leds.md)).
33. **The last SRAM write before a spin is lost at a watchdog reset**
    unless another write follows ([hardware.md](hardware.md),
    `commit_terminal()`). The manual says nothing about a posted-write
    buffer. **Inferred:** a write buffer on the SRAM path that only a later
    write drains.
34. **The `WDTPRE` encoding is no longer an assumption**: `100` is /16
    (p. 71), as `kb/watchdog.c` guessed.
35. **Package pitch:** the manual's LQFP80 is 0.4 mm pitch on a 10 mm body
    (p. 267); [battery.md](battery.md) records the `HFD80CP100` clone as
    "0.5 mm pitch". Measure before buying a socket or test clip.
36. **SysTick priority may be 0 instead of 3** (`SN32_ST_IRQ_PRIORITY 8`
    overflowing the 2-bit field; [section 5](#5-interrupts)). Unverified.
37. **Code straight after a Deep-sleep WFI in flash can run stale
    instructions** (measured 10-20; nothing in the manual). On
    `b2a07e0d37` every wake from Deep-sleep went wrong the same way. It
    depended only on where the linker put the WFI, which was checked at
    seven placements of the same code, each as predicted:
    - **It failed every time** with the WFI at 2 mod 8, the second half of
      an aligned 8-byte block's first word, and straight-line code after
      it.
    - **It held** at 6 mod 8, and wherever a branch came straight after
      the WFI.

    The evidence fits the next block's first fetch returning the stale
    block, so its halfwords run in place of the next ones. That is a
    hypothesis; the register capture has not been run. A data read from
    SRAM, a few cycles after the wake, always came back right (102 wakes).
    **The workaround, in every build since `8b06e4dcc4`:** enter and leave
    Deep-sleep from SRAM, and touch the flash only after ~1,300 cycles and
    one dropped read (`sleep.c`, `ds_deep_wfi`).
    [`plans/DEEP-SLEEP-REGRESSION-2026-10-20.md`](../plans/DEEP-SLEEP-REGRESSION-2026-10-20.md).

## 14. What the manual does not say

The open questions, roughly in the order the sleep work will meet them.
Each wants a measurement on the bench ([test-bench.md](test-bench.md)), not
more reading.

1. **The clock after Deep-sleep wake**: is the PLL still selected and
   locked? (p. 76 is silent.)
2. **What `WFI` does with `PMU_CTRL = 0`.**
3. **Whether SysTick runs in Sleep** (p. 41 hedges), and so whether
   ChibiOS deadlines slip during light sleep.
4. **Whether the USB PHY really drops in PMU Sleep** (p. 78 against
   p. 245), and whether the host notices.
5. **The current in Sleep at 48 MHz**: the manual's only Sleep figure is at
   32 kHz.
6. **Whether the WDT counts in Deep-sleep** with the RTC holding the ILRC on.
   **Answered: it does not** (10-18 and 10-28, `history/wdt-asleep-20261028-2330/`).
7. **VREG33 in Deep-sleep**, and where VDDIO1 (the LCD's and flash's
   supply) comes from.
8. **Whether a GPIO edge interrupt works on a pin a peripheral owns**
   (UART2 RX, to wake on the CH582F).
9. **The UART FIFO depth.**
10. **Which register powers the flash down in Deep-sleep**, and the wake
    cost (p. 75). Nor how long after the wake the flash is safe to fetch
    from: errata item 37 is where that bites.
11. **The boot ROM's USB protocol**, its entry point (`0x1FFF_0301` is
    QMK's) and the `0x3FFFC` flag.
12. **The SRAM write buffer** behind item 33 of the errata.
13. **The "SPI FLASH" window at `0xA000_0000`** in the memory map (p. 39).
