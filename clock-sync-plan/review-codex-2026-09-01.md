## Verbatim findings

1. **Critical — §3.6 boot acquisition / §4 `rtc_fast_task()`: the “non-blocking” PCF polling path can reintroduce keystroke-eating LCD waits.** The proposed task runs per iteration “next to `display_blit_pump()`” and every read invokes the bus guard. Today the pump runs first and can arm a DMA on every pass (`ak820pro.c:434-440`); `rtc_bus_guard()` then calls blocking `lcd_blit_wait()` (`rtc/rtc.c:101-109`). That wait can spin for a full transfer or up to the 250 ms recovery bound (`graphics/lcd_bus.c:628-695`). Polling immediately after the pump therefore serializes the intentionally asynchronous glyph queue and can create repeated multi-millisecond scan holes—the exact failure the queue was designed to eliminate (`lcd_bus.c:510-521`, `648-667`). The claim that only the splash causes one wait is false. **Fix:** never drain a blit from `rtc_fast_task()`. Run it before the pump and skip the I2C operation whenever `lcd_blit_busy()` is true; retry on a later pass. Measure actual scan gaps under an active clock/text repaint before accepting the design.

2. **Critical — C2, §3.5–3.6, §7.10: “No path can hold the main loop >1 ms” is contradicted by the actual I2C and bus-guard code.** Every transaction has a 20 ms I2C timeout (`rtc/rtc.c:24-27,118-125,174-180`), and its guard may wait on LCD DMA as described above. The host-set handler also performs STOP plus an eight-byte time write synchronously (§3.5), so it adds another blocking transaction to an already blocking HID path. The plan’s “≤200 µs” figure is only an expected successful bus time, not a bound. **Fix:** state the real worst-case bounds; make all new PCF operations opportunistic state-machine steps that return immediately if DMA is active; add transaction duration/timeout counters and require no >1 ms gaps attributable to the new path.

3. **High — §3.3 slew arithmetic is off by one.** The plan correctly defines `P` as the register value and a period as `P+1` cycles (§2, §3.2). Shortening by `d` cycles requires a new register value `(P+1-d)-1 = P-d`, but §3.3 writes `P-d-1`. Even with `d=0`, this makes every “steady” slew period one tick short. The LLD also treats its argument as the register value (`hal_rtc_lld.c:267-279`). **Fix:** use `SECCNTV = P - d`, document all variables as either register values or cycle counts, and add exact tests for `d = 0, ±1, ±SLEW_STEP`.

4. **High — §3.1’s fractional read is not coherent when SECIF is pending or delayed.** The retry only detects execution of `rtc_second_cb`. Hardware can reset/roll `SECCNT` at the second event while the RTC ISR is masked or delayed, leaving `rtc_seconds_count` and software `rtc_time` on the previous second. The loop can then return an old whole second paired with a near-zero new-period fraction. This is especially relevant because internal-flash programming masks interrupts, which the plan itself acknowledges. The software time is incremented only in the ISR (`hal_rtc_lld.c:110-124`). **Fix:** include `SN_RTC->RIS & SECIF` in the coherence protocol, or take a locked snapshot that rejects/retries while SECIF is pending. Explicitly test reads during forced flash programming and higher-priority ISR load.

5. **High — §3.4’s 11-bit `FRMNO` rejection cannot detect all delayed ticks.** Modular subtraction aliases delays separated by 2048 ms. A roughly 3.0 s delayed RTC callback can produce a modulo delta in the accepted 900–1100 range and contaminate the window. The assertion that windows spanning suspend, unplug, or “>1 s” delay are necessarily rejected is therefore false. `FRMNO` is only 11 bits (`SN32F290.h:4653-4659`). **Fix:** qualify samples with USB driver state and an independent elapsed-time/RTC-pending continuity check; invalidate the entire window after any suspected delayed SECIF, suspend, reset, or discontinuity. Do not infer liveness from modulo delta alone.

6. **High — §3.4’s estimator can overflow 32-bit arithmetic.** At 128 samples and a 40,000-cycle period, `win_ticks` is about 5.12 million; `win_ticks * 1000` exceeds `UINT32_MAX`. The pseudocode does not specify 64-bit promotion. **Fix:** require `uint64_t` accumulators or cast before multiplication, then range-check the quotient before narrowing to `P_target`.

7. **High — §3.2–3.4 and §4 leave `RTCD1.period` incoherent with the hardware.** The pseudocode writes `SN_RTC->SECCNTV` directly for the first period, restore, and slew. The LLD’s cached period changes only through `rtc_lld_set_period()` (`hal_rtc_lld.c:267-301`), while existing `rtc_get_period()` returns that cache (`rtc/rtc.c:300-304`). Yet §4 simultaneously says direct register writes are used and that `rtc_lld_set_period` is used for the phase set “so `rtcp->period` stays coherent.” Both cannot be true. Status replies, fractional conversion, persistence, and later calculations can report/use a stale value. **Fix:** define one owner API that atomically updates the hardware and cached state from both ISR and thread contexts, or remove the cache and read the register consistently. Specify whether reported `period` is steady-state `P` or the currently active first/slew period.

8. **High — §3.5’s missed-release recovery is incomplete and can set the PCF one second wrong.** The plan writes PCF registers for boundary `S`, then says a late release is “re-armed for the next second with `S+1`.” Merely changing the deadline does not change the already-written PCF value. Releasing one second later while it still contains `S` makes it one second behind. Rewriting also adds another blocking transaction and must correctly handle minute/day/month/year rollover. **Fix:** on a missed release, rewrite the complete calendar value for the new target boundary before scheduling release, using tested calendar arithmetic; alternatively abort and restart the entire STOP/write/release state machine.

9. **High — §3.5’s release deadline is checked before a potentially long bus-guard wait, so its claimed ±2.5 ms timing does not hold.** `now ≥ T_rel` is evaluated, then the release write calls `rtc_bus_guard()`, which can block until DMA completion or timeout. The actual STOP-clear instant may therefore be tens or hundreds of milliseconds later than the checked timestamp. **Fix:** release only when the bus is already idle; otherwise declare the window missed without entering the guard. Timestamp immediately around the actual I2C operation and compensate its measured write latency.

10. **High — §3.6 cannot reconstruct a correct full timestamp from one-byte seconds polling as written.** The current only PCF read fetches all seven time registers (`rtc/rtc.c:111-155`). A proposed one-byte primitive can detect an edge, but `rtc_set_time_ms(pcf_time, 0, step)` still needs a coherent date/hour/minute/second. A cached seven-byte read becomes wrong at minute, day, month, or year rollover, while a full read after edge adds latency and needs rollover-safe consistency. VL is also in the seconds byte, but other BCD validity still needs checking. **Fix:** specify a coherent algorithm: bracket on seconds, then read all seven registers, re-read seconds to reject rollover, and timestamp/compensate the full-read latency. Test every calendar rollover.

11. **High — §3.6’s polling load is materially understated.** Approximately 400 bit-banged transactions per boot second means roughly 4–8% bus/CPU occupancy even under the optimistic 100–200 µs estimate, plus pin-mode changes and possible DMA deferrals. The main loop is only about 2.5 ms (`ak820pro.c:190-197`). This is not “only reads” from a typing-safety perspective. **Fix:** reduce polling frequency to a measured safe cadence, start only after splash/display initialization, skip busy-DMA passes, and gate Phase 3 on loop-gap frequency—not merely maximum—and real keystroke counts during acquisition.

12. **High — §3.7–3.8’s old-firmware fallback cannot work as described.** Raw HID reports are always read as 32 bytes (`ak820ctl.c:72-83`), and requests are zero-padded (`ak820ctl.c:74-75`). Old firmware echoes the buffer, so an old `GET_TIME` naturally returns zeros in bytes 11 onward. There is no absent “reply length,” and zero flags are a valid new-firmware state before sync. **Fix:** add an explicit protocol-version or fixed capability/magic byte in the extended reply. Fall back only when that marker is absent.

13. **High — scheduled `--no-wait` sync has no backward-compatible fallback in wireless slider positions.** The existing agent deliberately uses fire-and-forget because replies disappear in BT/2.4G (`ak820-clocksync.sh:10-18`; `ak820ctl.c:86-101`). The proposed `--no-wait` sends only command `0x03`; old firmware will ignore it, and the host cannot issue `GET` to discover that in those positions. This contradicts the general fallback claim. **Fix:** version-cache capability from a prior wired session, or define a backward-compatible single command. Do not blindly send both commands unless double application and PCF writes are proven harmless.

14. **High — §3.7’s “equivalent accuracy” RTT algorithm is underspecified and not equivalent to an NTP exchange.** A `GET` reply timestamps the board when `rtc_read_into()` runs, while the host observes send and receive times. Merely taking minimum RTT and sending `now + RTT/2` does not account for the time between the GET measurement and SET construction, HID scheduling delay, or request/reply asymmetry. Existing raw-HID reads can wait up to two seconds (`ak820ctl.c:73-83`), and the claimed 1–2 ms latency has not been demonstrated in the plan. **Fix:** specify host send/receive timestamps and board receive timestamp semantics precisely. Prefer an actual four-timestamp exchange or, at minimum, have SET carry the host timestamp captured immediately before `hid_write`, measure arrival error over many trials, and derive a bounded uncertainty before promising ±3/10 ms.

15. **High — §3.5 clobbers the entire PCF Control_status_1 register.** Writing literal `0x20` and later `0x00` does not preserve any other control bits. The plan assumes STOP is the only state worth retaining but provides no read/modify/write or initialization invariant. **Fix:** read and preserve supported bits, modify only STOP, and document what happens to TEST1/TESTC-related state on this clone. Validate the post-release register.

16. **Medium — repeated SECCNTV writes inside the ISR add unmodelled time to slewed periods.** Writing `SECCNTV` resets `SECCNT`; when done after ISR entry, the effective interval includes the match-to-write latency. During a slew this happens every second, but `win_ticks` counts only programmed counter cycles. The estimator therefore attributes ISR/reset latency to ILRC frequency. The plan only discusses compensating the one-time first period (§3.2), not repeated slew writes. **Fix:** either suspend frequency estimation during slews, include measured write-phase overhead, or implement a period mechanism that does not reset after every tick. Verify under competing priority-1/2 interrupts, not only idle means.

17. **Medium — §3.4 has no fully specified state handoff between SOF discipline and PCF fallback.** “`d == 0` for three ticks” handles a frozen register, but no rules are given for clearing partial SOF windows, invalidating `fn_last`, cancelling/restarting a PCF calibration span, choosing which pending `P_target` wins, or returning from fallback after USB resumes. Phase 2 also calls the fallback “existing PCF trim unchanged,” while §3.4 says it has edge bracketing and slew—features deferred to Phase 4. **Fix:** define an explicit reference-source state machine with entry/exit actions, window invalidation, ownership of `P`, and phase-correction policy. Make Phase 2 use either the genuinely unchanged existing fallback or move bracketing into Phase 2.

18. **Medium — first-period and current-period status semantics are insufficient for correct fractional conversion.** §3.1 divides `SECCNT` by the returned `period+1`, but during a shortened first period or slew the active period differs from steady `P`. §3.7 exposes only one period value, while §4 implies `rtc_get_period()` remains the cached steady period. This yields wrong fractional timestamps exactly while correcting the clock. **Fix:** snapshot `SECCNT` together with the active cycle count that produced the current interval; expose both active and nominal periods if diagnostics need both.

19. **Medium — the new command’s input validation is missing.** Existing code validates all seven legacy fields before touching the battery-backed RTC (`hid_protocol.c:22-50`). The plan does not require `ms <= 999`, reject reserved flags, validate actual month/day combinations, or prevent arithmetic overflow at date rollover. A value such as `ms=65535` underflows `R`; malformed calendar dates are currently normalized by `mktime`. **Fix:** define and test complete validation before any STOP, PCF, or SN32 write. Reject impossible dates and unknown flag bits.

20. **Medium — §3.2’s legacy mapping is not honestly compatible with arbitrary existing senders.** Mapping every whole-second packet to `ms=0` asserts that it arrived exactly on a boundary. Only the current `ak820ctl` attempts boundary alignment (`ak820ctl.c:119-181`); VIA, third-party tools, delayed hosts, and `--no-wait` under load are not guaranteed to do so. This can deliberately inject almost a full second of phase error. **Fix:** preserve legacy behavior unless the sender opts into phase semantics, or interpret legacy packets using measured arrival phase/explicit capability negotiation. Do not change command `0x01` semantics globally based on one host implementation.

21. **Medium — the goal is incompatible with optional SOF-offset correction.** The plan promises ±50 ms indefinitely with cable present (§0), but acknowledges a standards-compliant 500 ppm SOF error, which can create 300 ms between ten-minute host syncs (§3.4), and makes correction optional in Phase 4. Phase 2’s required “≤20 ms at all times” cannot be guaranteed under the stated SOF assumption. **Fix:** either make SOF-offset learning mandatory before claiming the goal, shorten host sync cadence enough to meet the bound at ±500 ppm, or weaken the guaranteed bound to a measured property of this host.

22. **Medium — “no on-enumerate trigger is needed” leaves a large correctness hole.** If a scheduled sync was missed during sleep/unplug, or the PCF STOP sequence failed, the clock can remain wrong for up to ten minutes after enumeration. Boot acquisition only reproduces the PCF’s state; it cannot make a stale or incorrectly phased PCF true. **Fix:** trigger a host sync on device enumeration/wake when possible, retaining the periodic job as backup.

23. **Medium — Phase 3’s unplugged acceptance criterion is numerically wrong.** At the stated 58 ppm, eight hours is about 1.67 seconds, before boot acquisition uncertainty and any PCF write error. Requiring only `≤2 s` leaves almost no margin and does not validate the claimed phase-correct PCF write to ±10 ms. Conversely, it is too loose to distinguish a correct STOP sequence from many substantial phase errors. **Fix:** separately test immediate post-write/reboot phase (tens of milliseconds) and rate drift over eight hours against the measured oscillator bound plus explicit margin.

24. **Medium — the BT verification plan admits that its proposed evidence is destroyed.** Phase 2 says to read health after flipping wired, then immediately notes that the flip wipes counters (`PLAN.md:390-393`). The backlog confirms raw-HID replies are unavailable in BT and the flip power-cycles the board (`hardening-plan/BACKLOG.md:45-52`). Console availability/routing in BT is not established here. **Fix:** implement the already-backlogged on-LCD snapshot or persist/test-latch the relevant counters before claiming a BT typing-safety gate.

25. **Low — §6 says no new instruments are needed, but the plan explicitly requires several.** Phase 0 adds `HC_RTCTEST`, extended GET, and `HC_RTC`; §4 adds new logging and an `HC_DRIVE` operation. These are material firmware and host-tool changes, not existing instruments. **Fix:** correct the claim and put instrumentation implementation/validation before any phase that relies on it.

26. **Low — C3 is internally inconsistent about the persistence threshold.** The hard-constraint table says the existing “≥32-tick change” is retained (`PLAN.md:35`), while §3.4 and the code map change it to 64 (`PLAN.md:222-225,324`). The actual source uses 32 (`rtc/rtc.c:433-436`). **Fix:** state 64 consistently and document that it changes write frequency but not the deferred flash mechanism.

27. **Low — several “verified” timing and priority claims are stronger than the source supports.** Priority 3 is not uniquely “the lowest”; the PWM row interrupts also use priority 3 (`mcuconf.h:84-89`). The register header proves `FRMNO` is an 11-bit SOF frame number but not that it advances with SOF interrupts disabled or in every slider/power state (`SN32F290.h:4653-4659`). Those are correctly listed for hardware verification later, so C1 should not present their consequences as settled. **Fix:** describe priority 3 as equal to the row ISR’s configured priority and keep FRMNO behavior explicitly conditional until Phase 0 passes.

Things checked and found correct:

- The patched LLD really maintains absolute time in software, increments it in SECIF, and `rtc_lld_set_time()` does not touch the prescaler (`hal_rtc_lld.c:46-51,110-124,185-193`).
- `SECCNTV` and read-only `SECCNT` exist at the stated register offsets, and `FRMNO` is an 11-bit read-only register (`SN32F290.h:2910-2912,4653-4659`).
- QMK’s `usbcfg` does not initialize `sof_cb`, and the LLD enables SOF interrupts only when that callback is non-null (`usb_main.c:320-324`; `hal_usb_lld.c:480-484`).
- USB IRQ priority is 1 and RTC IRQ priority is 3 (`hal_usb_lld.h:76-77`; `hal_rtc_lld.h:74`).
- Raw-HID replies are indeed unusable from the USB-side tool in wireless routing, while fire-and-forget writes are intentionally supported (`ak820ctl.c:86-101`; `hid_protocol.c:283-290`).
- Existing RTC persistence is deferred/coalesced, uses a five-second settle period, and currently requires a 32-tick change after ten minutes (`kb_eeconfig.c:34-50,71-75`; `rtc/rtc.c:433-436`).
- The display reads whole RTC time and schedules repaint from `rtc_seconds_count`, so leaving fractional time out of the display path is consistent with current behavior (`display.c:459-487,1629-1639`).
- The phase-set sign convention is sound: positive `true-board` offset requires a shorter interval to advance the board.
