# Codex review — 2026-08-31

External review of this plan by Codex CLI 0.151.0 (`codex exec`, read-only
sandbox, full repo access). All 16 findings were assessed; key factual claims
(existing SN32 WDG LLD, `bootloader_jump()` reset path, `kb_config_t` pad
bytes, disabled UART RX FIFO, TX-queue drop path) were verified against the
source before acceptance. Every finding was folded into the phase files on
the same date. Verbatim findings:

1. **Critical — Phase 3.2 models orthogonal CH582F activity as one mutually exclusive state machine.** The proposed enum (`idle/selecting/bounce-wait/attempting/advertising/connected/rejected`) cannot faithfully represent the current overlapping concerns: observed radio state, desired profile, optimistic UI state, pending pairing retries, cancel-pairing bounce, cold-boot recovery, and the independent ACKed TX queue. For example, pairing is shown optimistically while `A6 51` is still retrying ([ch582f_ajazz.c](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/bluetooth/ch582f_ajazz.c:470)); bounce temporarily selects another slot while the desired target remains unchanged ([ch582f_ajazz.c](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/bluetooth/ch582f_ajazz.c:414)); and the TX queue operates independently of connection state. Flattening these into one enum will either create a combinatorial state explosion or silently discard valid simultaneous conditions. Phase 3.2 should instead use separate explicit machines—at minimum `observed_link_state` plus `pending_control_action`—while leaving TX reliability independent. The fallback `pending_action` structure is the safer initial change and should be the default, not merely a retreat option.

2. **Critical — the watchdog is being treated as safe recovery before reset-during-flash behavior is established.** A watchdog can fire while internal EFL is programming, erasing, or wear-leveling metadata. That may turn a recoverable stall into corrupted eeconfig/dynamic-keymap state or a reboot loop. The plan tests normal provisioning and a generic infinite loop, but not timeout/reset injection during an internal-flash transaction. Before enabling WDT generally, test or prove atomic recovery of `wear_leveling_efl` after reset at each program/erase boundary, validate defaults after a damaged logical store, and preserve a way to boot with the watchdog disabled. This belongs before the phase-1 “blast-radius cap” claim and before phase 4 adds more writes.

3. **High — the watchdog proposal overlooks that an SN32 WDG driver already exists and therefore scopes the implementation incorrectly.** ChibiOS-contrib already contains the SN32F2xx WDG LLD at [hal_wdg_lld.c](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/lib/chibios-contrib/os/hal/ports/SN32/LLD/SN32F2xx/WDT/hal_wdg_lld.c:74), and the SN32F290 platform already includes its build file. Phase 1.1’s likely “bare-register, ~20 lines” path would duplicate hardware code and bypass ChibiOS state handling. Enable `HAL_USE_WDG`/`SN32_WDG_USE_WDT`, audit this lightly tested LLD, and use `wdgStart`/`wdgReset`/`wdgStop`. Also note the reset-cause breadcrumb is available: the SN32 headers expose `RSTST.WDTRSTF`; this is not merely hypothetical.

4. **High — kicking “from `housekeeping_task_kb()`” is underspecified and can certify only entry, not a completed healthy pass.** The kick must be at the very end, after the 10 Hz RTC/animation/display work and after `housekeeping_task_user()` ([ak820pro.c](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/ak820pro.c:1258)). Kicking at entry gives every newly entered pass another three seconds even if it wedges immediately afterward and does not prove downstream tasks completed. Initialization should start the watchdog only after `keyboard_post_init_user()` returns. Add tests for stalls inside RTC I2C, LCD teardown, user housekeeping, and flash hooks—not only a top-level spin.

5. **High — bootloader safety requires a concrete code change, not just verification.** The SN32 boot path writes RAM magic and immediately calls `NVIC_SystemReset()` ([sn32_dfu.c](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/platforms/chibios/bootloaders/sn32_dfu.c:28)). Nothing currently stops WDG first. Override `bootloader_jump()` or add a board hook that calls `wdgStop()` before setting the magic/resetting, then test both `QK_BOOT` and watchdog-reset reboot paths. Also verify whether WDT configuration survives system reset; otherwise the bootloader’s infinite tail at line 45 can be reset unexpectedly. This is a release blocker, as phase 1 correctly suspects, but it should be specified as an implementation requirement.

6. **High — Phase 2’s concurrency model is factually wrong for the CH582F driver.** UART2 ISR context does not mutate `conn_state` or the timer/flag pairs; the ISR feeds ChibiOS’s serial queue, while parsing and all transitions occur in main-loop `ch582_task()` ([ch582f_ajazz.c](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/bluetooth/ch582f_ajazz.c:550)). Marking these variables `volatile` does not make them ISR-shared and obscures the real ownership model. The audit should trace call context rather than infer it from the peripheral. Documenting “UART ISR owns RX buffering; main loop owns parser/state/TX queue” is a cheap, high-value simplification and substantially lowers phase-3 rewrite risk.

7. **High — the soak harness’s pass criterion contradicts the measured healthy baseline.** Phase 1.3 fails on *any* health-counter increase, yet CLAUDE.md records a healthy sustained BT rate of roughly 0.042 ACK timeouts per frame. A real BT workload will therefore fail by design. Use rate/ratio thresholds over a minimum sample count, fail immediately only on drops, reset loops, liveness loss, or LCD timeout, and separate boot traffic because CLAUDE.md says it runs around 0.58 timeout/frame. Similarly, scan rate and main-loop gap need tolerance bands, not equality/change detection.

8. **High — the harness must serialize raw-HID transactions even while stressing firmware paths concurrently.** Multiple outstanding VIA-style writes, RGB commands, text pushes, and `ak820ctl info` requests on one raw-HID interface can interleave replies or consume each other’s responses, producing false liveness failures. Use one owning process and one request/reply dispatcher; schedule operations at overlapping firmware cadences but permit only one reply-bearing transaction in flight. Write-only text packets may be injected between transactions. Also test mode-switch interruption separately: CLAUDE.md explicitly says switching during flash provisioning destroys the already-erased asset image.

9. **High — Phase 0’s “local-only submodule branch is acceptable” contradicts its fresh-checkout exit criterion.** A superproject gitlink pointing to a commit that exists only in one local clone is not reproducible anywhere else. `.gitmodules` does not transport that object, and its `branch` setting does not replace the pinned gitlink semantics. The patched commit must exist on a reachable remote, or the patches must be applied reproducibly during checkout/build. This directly invalidates [phase-0-lockdown.md](/Users/jdlien/code/ak820-pro/hardening-plan/phase-0-lockdown.md:36).

10. **Medium-high — Phase 3.2 incorrectly proposes folding parser fixes into the behavioral rewrite.** That violates the plan’s own “one change per flash” rule and removes the clean baseline needed to distinguish parser regressions from transition regressions. Parser resynchronization already exists as a rolling three-byte window ([ch582f_ajazz.c](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/bluetooth/ch582f_ajazz.c:550)); any additional validation or counters should land and soak independently before restructuring control state. The rewrite should then be semantic-preservation-only.

11. **Medium-high — the CH582F verification matrix cannot exercise the key failure modes deterministically enough.** Ordinary pair/unpair cycles may never reproduce a missed `5B 32`, lost ACK, dropped `A6 51`, truncated frame, or delayed `5B 23`. Add a compile-time fault-injection shim between serial input and parser that can drop, delay, duplicate, and corrupt selected three-byte frames, plus deterministic transition traces. Otherwise “green soak” mostly proves the happy path, while the rewrite’s purpose is preserving recovery from rare wire failures. A host-side model test of the transition reducer is especially valuable and costs no MCU time.

12. **Medium — Phase 1’s unified health line risks becoming continuous console traffic.** “On change only” is unsuitable for scan rate, which naturally jitters, and worst-gap maxima may update repeatedly during warm-up. CLAUDE.md documents that console traffic and duplicate console processes can perturb the host and timing. Quantize scan rate into tolerance bands, suppress startup, rate-limit output, and snapshot counters atomically under a very short lock before formatting. Keep cumulative counters available through raw HID as well; console-only observability disappears during precisely the stalls being investigated.

13. **Medium — the audit misses queue-overflow and stale-input behavior as first-class robustness risks.** `ch582_send_command()` drops a full TX frame when its 23 usable entries fill, explicitly including key releases ([ch582f_ajazz.c](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/bluetooth/ch582f_ajazz.c:387)). Retrying state reports does not repair a release that was discarded after a newer press was queued. Audit whether keyboard/consumer reports should replace an older queued report of the same type, reserve capacity for releases, or force a neutral-state report after overflow. Also evaluate enabling the UART RX FIFO: the current configuration disables it, leaving only an ~87 µs service window at 115200 baud despite the ~39k interrupt/s load. Both are cheap, potentially high-value wins absent from the plan.

14. **Medium — Phase 4 overlooks the existing reserved bytes and existing immediate BT-profile writes.** `kb_config_t` already reserves three bytes after `bt_profile` ([ak820pro.c](/Users/jdlien/code/ak820-pro/qmk_firmware-ak820pro/keyboards/a_jazz/ak820pro/ak820pro.c:28)); `rtc_period` plus `lcd_brightness` fit exactly without changing block size or invoking uncertain versioning. Conversely, `save_bt_profile()` writes immediately on every slot change at line 43, contradicting phase 4’s shared “write once on settle” discipline. Define the four-byte layout explicitly, add validity/version semantics within it if needed, and move all kb-config persistence—including BT profile—through one coalescing deferred flush.

15. **Medium — the proposed RTC “settled” detector is not justified by the algorithm.** Phase 4 assumes correction magnitudes shrink monotonically and suggests two steps below 16 ticks. The implementation only trims when accumulated tick/reference error reaches at least two seconds, so near convergence its measurement window can become extremely long, and quantization or temperature change can produce non-monotonic steps. The cited trace merely happened to decrease. Persist each accepted, sanity-checked trim through a heavily coalesced policy—such as after a minimum uptime and only when sufficiently different from stored—or explicitly cap the observation window. Otherwise the value may never persist in ordinary sessions.

16. **Medium — reset recovery needs loop detection and a degraded-mode escape.** A deterministic boot-time failure in LCD, RTC, corrupt eeconfig, or WDG setup will produce endless three-second resets, potentially while battery-powered. Record consecutive watchdog resets in retained RAM or a carefully designed durable mechanism, and after a small threshold boot with risky subsystems disabled or leave WDT off long enough for recovery/flashing. The optional one-tick LCD marker is not useful when the LCD itself is the failing subsystem; the reset cause should be queryable through raw HID and console after recovery.
